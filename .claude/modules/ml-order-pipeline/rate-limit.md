# Bling API rate limit — ML order pipeline

É por CONTA, não por app/OAuth client. Confirmado em developer.bling.com.br/limites: 3 req/s, 120k/dia, compartilhado pela conta inteira. `waitForBlingRateLimit()` (`bling/api/bling_api.service.ts`) é o limiter leaky-bucket único backed por Redis (Lua `EVAL` atômico), chamado tanto pelo interceptor `onRequest` da instância axios `blingApi` quanto pelos dois scrapers Playwright/cookie-session que bypassam essa instância inteiramente (`get-stock-movements.ts`, `nfe-manifest-web-scraping.service.ts`).

**Revisitado**: usuário reportou 429s "estourando toda hora" apesar do interval já bem abaixo do limite no papel. Dois gaps reais:
- `handleBlingOAuthCallback`'s token-exchange `fetch()` não tinha timeout nenhum — adicionado o mesmo timeout de 30s que `doRefreshToken` já tinha.
- Toda chamada de escrita à Bling (POST/PUT/PATCH) em vários queues chamava `blingApi.get/post/put/patch` direto, sem o buffer extra de pacing `BLING_ORDER_REQUEST_DELAY_MS` que só o helper `blingGet` aplicava. `get-with-sleep.ts` agora exporta `blingGet`/`blingPost`/`blingPut`/`blingPatch` — todos os quatro aplicam o mesmo pacing + timeout explícito por chamada (`BLING_REQUEST_TIMEOUT_MS`, default 20s; geração de NFe override pra 45s).
- `BLING_RATE_LIMIT_INTERVAL_MS` default elevado 1500ms → 2000ms pra folga extra, a pedido explícito do usuário.

## Root cause real encontrado depois: race no próprio mecanismo de dispatch do limiter

Teste controlado em produção: pausar toda fila da Bling exceto uma de cada vez produzia zero 429s; rodar várias juntas reintroduzia bursts, mesmo todas compartilhando o mesmo limiter. O design "leaky bucket" anterior (`RESERVE_SLOT_SCRIPT`) pré-reservava um timestamp futuro de dispatch via script Lua atômico, depois fazia `await sleep(delayMs)` e disparava incondicionalmente quando o sleep resolvia — cada reserva individual era livre de race, mas **nada reverificava nada no momento real do dispatch**. Sob um event loop mais ocupado (mais filas rodando concorrentemente no mesmo processo), vários timers reservados independentemente podiam ficar todos atrasados ao mesmo tempo e disparar em sequência assim que o loop liberasse, sem gap entre eles. **Fixed**: `waitForBlingRateLimit()` redesenhado de "reserva um slot futuro, dorme cego, depois dispara" pra um loop atômico de **check-and-claim-or-wait** — um novo script (`TRY_DISPATCH_SCRIPT`) só rastreia o timestamp do último dispatch *realmente concedido*, e a cada chamada ou concede imediatamente ou retorna quanto esperar; o chamador dorme esse tempo e **volta a checar atomicamente** em vez de assumir que o sleep foi preciso. Sob contenção, só um chamador pode ganhar cada checagem atômica; todo outro chamador acordado ao mesmo tempo é forçado a esperar e retentar — espaçamento real ≥`BLING_RATE_LIMIT_INTERVAL_MS` entre dispatches reais vale independente de quão agrupados os wake-ups estejam.

## Env: `BLING_RATE_LIMIT_INTERVAL_MS` — fixed, faltava em 6 de 6 serviços do `docker-compose.yml`

Confirmado e corrigido: `docker-compose.yml` propagava `BLING_ORDER_REQUEST_DELAY_MS` pra todo service block relevante mas nunca propagava `BLING_RATE_LIMIT_INTERVAL_MS` pra nenhum — todo container caía no default do código independente do que fosse setado no ambiente/`.env`, ignorando silenciosamente qualquer override do operador. **Fixed** adicionando `BLING_RATE_LIMIT_INTERVAL_MS: ${BLING_RATE_LIMIT_INTERVAL_MS}` junto da linha `BLING_ORDER_REQUEST_DELAY_MS` já existente nos 6 service blocks. Se uma nova env var de pacing Bling for adicionada depois: lembrar que `docker-compose.yml` precisa dela em cada service block individualmente — não há bloco de env compartilhado/herdado neste arquivo.

## 429 com limiter saudável → tráfego de fora + jobs órfãos

Log do `[BlingApi][ReqCounter]` com gap sempre ~`BLING_RATE_LIMIT_INTERVAL_MS` e `#1 neste segundo` (chave Redis global, todos os containers) mas 429 frequente = cota da conta consumida por algo que não passa pelo limiter (outro ambiente com Redis próprio — ex. `docker-compose.dev.yml` — apontando pra mesma conta, outras integrações autorizadas na conta, XHRs internos da página nos scrapers Playwright). Retry de 429 passa de novo pelo `onRequest` → limiter, então não fura o espaçamento.

- Diagnóstico: `waitForBlingRateLimit(label?)` loga `MÉTODO url` no ReqCounter; o 429 loga `body` + `headers` da resposta (identifica qual limite estourou).
- `maxProcessingMs` da fila precisa cobrir o pior caso do retry 429 (3+6+12+24+48s + espera no limiter por chamada). O watchdog do `BaseQueueService` usa `Promise.race`, não cancela o `process()`: abortar cedo deixa execução órfã ainda batendo na Bling **e** o BullMQ refaz o job (`attempts: 5`) → tráfego duplicado. Filas que chamam a Bling: ≥5 min (`BLING_ORDER_INGESTION`, `CNPJ_VERIFY_CNAE`, `NFE_EMISSION` etc.).
