# Bling NFe web-scraping automation

`.../bling-nfe/automations/auto-manifest/`

- `BlingManifestacaoService`/`BlingNfeScrapingQueue` (queue `BLING_NFE_SCRAPING`, runs on `worker-scraping`, every 3h) automates "manifestar nota como operação realizada" through Bling's own web UI (`notas.entrada.php`) via Playwright — no public API for this action. Uses a persistent browser profile (`./bling_session`) shared with `get-stock-movements.ts`, which logs in the same way but against `estoque.php`.
- **Fixed — login failed 100% of runs on this flow only**, while `get-stock-movements.ts` worked fine with the same credentials/profile. Root cause: `ensureLoggedIn`/`doAutoLogin` checked `page.url()` right after `waitUntil: "domcontentloaded"` — too early for Bling's SPA to render, so the login-diagnostic screenshot (added at the same time, mirroring `get-stock-movements.ts`'s `logLoginPageState`) showed an unrendered page (`#username=0`, empty body) that looked like a login wall. `get-stock-movements.ts` already used `waitUntil: "networkidle"` + a settle wait; this file used `domcontentloaded` with none. **Fixed** by switching both `page.goto` calls in the login flow to `networkidle` and adding the same ~1.5s settle wait. If either file is touched again: keep `networkidle` for Bling's pages — `domcontentloaded` isn't enough to trust `page.url()`/DOM state on a client-rendered page.
- **Fixed — login-failure diagnostic captured the wrong moment.** In both files' `doAutoLogin`, after clicking "Entrar" the code waited 4s then immediately `goto`'d the target page (`estoque.php`/`notas.entrada.php`) with `networkidle`; only *after* that round-trip did it check `isLoginWall`/capture `logLoginPageState`. If the login actually failed (wrong password, CAPTCHA, 2FA), Bling shows the real reason on the login page right after the submit — but by the time the diagnostic screenshot/body-text was captured, the code had already navigated away and back, landing on a **freshly reloaded, blank** login page with no error banner. So every login-failure log/screenshot only ever showed a generic empty login form, never the actual cause — this is why a production failure looked "nonsensical" (e.g. valid credentials in `.env`) with no way to tell wrong-password from CAPTCHA from a stale session from an account-side block. **Fixed** by adding an extra `logLoginPageState` capture immediately after the 4s post-submit wait, gated on `page.url().includes("/login")`, *before* the `goto` to the target page. Next time a login failure happens, check this earlier capture (in the log, the one logged first) for the real error text/CAPTCHA — the later "pós-login ainda na tela de login" capture is still just the blank reloaded page and isn't useful for root-causing *why* it failed, only *that* it failed.
- **Fixed — login "credenciais inválidas" despite correct email/password.** Both files' `doAutoLogin` located the password field with `page.locator('input[type="password"]')`, on the documented assumption that "only one field of that type exists on the page." Confirmed false (2026-09-17), and the two known layouts turned out to use *different* attribute schemes for the same field, discovered in two rounds:
  - **Classic layout** (in production): the real, visible password field is `<input type="text" ...>` (masked via JS, not natively) and carries `data-gtm-form-interact-field-id="1"` (username is `="0"`, a GTM analytics attribute). A *different*, hidden `input[type="password"]` also exists on the page — almost certainly an anti-bot honeypot targeting exactly the "just grab `type=password`" pattern. The script was filling the correct password into that hidden decoy field, leaving the real field empty, so Bling rejected the submit as invalid credentials — while a human logging in manually with the same credentials worked fine, which is what made it look "nonsensical." Diagnosing this required the previous bullet's fix: the immediate post-submit capture showed `senha=1` (i.e. `input[type="password"]` still matched *something* and `.fill()` didn't throw), which only makes sense if there's a second, wrong password-typed field.
  - **PrimeReact layout** (found testing locally right after the `data-gtm-form-interact-field-id="1"`-only fix): here the field genuinely IS `input#login-password[type="password"]` (a real PrimeReact `Password` component), but it does **not** carry `data-gtm-form-interact-field-id` at all — a selector relying only on that attribute times out on this layout instead.
  - The one attribute confirmed present on the real field in **both** layouts is the placeholder text `"Insira sua senha"`. **Fixed** by making the password locator `input[placeholder="Insira sua senha"], input#login-password, input[data-gtm-form-interact-field-id="1"]` (`.first()`) — placeholder as the primary cross-layout match, the other two as fallbacks if the placeholder wording ever changes. The classic layout's hidden honeypot matches none of these three (no placeholder, no id, no gtm attribute), so it's correctly excluded either way.
  - Lesson if Bling's markup shifts again: don't trust `type="password"` for this field, and don't assume one cross-layout attribute is enough — verify the *actual rendered DOM* of whichever layout is live at the time (`page.content()`/manual browser inspection), since the two layouts have historically diverged on both `type` and on which tracking/id attributes they carry.
- **Unconfirmed fix in progress — Bling blocks login with "Não permitido" even with correct, correctly-placed credentials.** Confirmed 2026-09-17 via screenshot: email/password are filled into the right fields (verified visually), yet Bling's login POST comes back with a generic `"Não permitido."` banner — not "senha incorreta", no CAPTCHA, no 2FA prompt. Manual login with the exact same credentials, same machine, same (non-headless) Chromium works fine, which rules out IP/account-level lockout as the sole explanation (same IP/network either way) and rules out headless-specific detection (both manual and automated runs were non-headless locally). The remaining difference is *how* the input was produced: `.fill()`/`.click()` set values and dispatch clicks synthetically with no realistic timing — a classic behavioral-biometrics bot signal (typing cadence, no pause before submit) that anti-fraud login systems score independently of credential correctness. **Attempted fix** (not yet confirmed against a real run): replaced `.fill()` with `.pressSequentially()` (real per-character key events with a randomized 70–160ms delay) for both fields, added randomized pauses (300–900ms) between filling username/password/hovering-before-click, and a `.hover()` before `.click()` on submit — same change in both `get-stock-movements.ts` and `nfe-manifest-web-scraping.service.ts` (new shared-pattern helper `randomDelayMs`, duplicated in both files like the rest of this login flow). If this doesn't clear the "Não permitido" block: the repeated failed automated attempts made while debugging the password-selector bug (see next bullet) may have separately tripped a rate-limit/temporary account-flag that needs a cooldown period regardless of typing speed — check by waiting and retrying, and by looking for a Bling security-alert email on the login account, before assuming the humanized-typing fix itself is insufficient.
- **Known follow-up, not yet done**: `BlingNfeScrapingQueue`'s `scheduleRepeat({ every: 3 * 60 * 60 * 1000 })` (`src/queues/index.ts`) has no `cron`/`tz` anchor, so it drifts across all hours of the day (anchored to whenever the process booted) and can land in the middle of peak webhook traffic instead of a predictable off-hours slot like `BLING_STOCK_MOVEMENTS_SCRAPING`'s `cron: "0 5 * * *"`.
