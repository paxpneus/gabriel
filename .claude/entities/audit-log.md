# AuditLog (`src/modules/global/audit-logs/`)

Tabela `audit_logs` (`m322`): `user_id` (FK users, nullable), `date` (default now), `entity` (`AuditEntity`, STRING — enum só no TS, entidade nova não precisa de migration), `internal_id`, `action` (`CREATE`/`UPDATE`/`DELETE`), `description` (TEXT), `changes` (JSONB). Índice `(entity, internal_id)`.

- **Gravação explícita na service, na transação do chamador** — `auditLogService.record(entries[], t)` (um `bulkCreate`). Sem hook Sequelize: hook não sabe o usuário e `bulkCreate`/`bulkUpdate` não disparam hook.
- **`description` é gerada** por `buildAuditDescription(entity, action, changes)` (`helpers/description.ts`) — texto pra usuário leigo: `ENTITY_LABELS` (Produto, Configurações do produto, Mapeamento DE x PARA, Mapeamento de integração), `FIELD_LABELS` (gtin → EAN, `is_physical_override` → "EAN físico confirmado"...), booleano sim/não, id técnico no fim entre colchetes. Nunca nome de tabela/coluna.
- **`changes`** (`AuditChanges`): `summary`, `before`/`after` da própria entidade, `affected[]` (outras entidades tocadas pela mesma operação, com before/after), `origin` (quando o log é reflexo de outra entidade). Operação que mexe em várias entidades grava **uma entrada principal** (com tudo em `affected`) **+ uma por entidade afetada** (com `origin`) — quem audita qualquer uma vê o impacto inteiro.
- **`description` é resumo, não detalhe**: campos da própria entidade (antes → depois) + origem + afetadas **só como contagem por entidade/ação** ("Mapeamento DE x PARA: 1 criação, 1 remoção; Configurações do produto: 2 alterações") — não cresce com nº de lojas/registros. Detalhe de cada afetada (rótulo, before/after, id) fica só em `changes.affected`.
- **Leitura**: `auditLogService.paginateByEntity(entity, internalId, params)` (paginado, `date DESC`, `perPage` limitado a 100, `filters[action]` só CREATE/UPDATE/DELETE — outro valor → erro, com `user { id, name }`) — genérico pra qualquer entidade; a service da entidade chama e expõe na própria rota. Hoje: `GET /api/products/:id/audit-logs` (`productService.findAuditLogs`, entidade PRODUCT; `[authenticate, userPermissions]` = leitura de Produtos, 404 se o produto não existe, 400 se o id não é uuid).
- **Texto**: ids técnicos (`id`, `product_id`, `unit_business_id`, `integrations_id`) não entram na description; em UPDATE só aparece campo presente no antes e no depois.
- **Quem fez**: controllers usam `getRequestUserId(req)` — application (API key) grava `user_id = null` (o id dela quebraria a FK).
- **Todo fluxo auditado que mexe num produto grava também uma entrada PRODUCT** (com o resto em `affected`), pra o histórico do produto ficar completo: Confirmar EAN físico, `createForProduct`, `createFromUnmapped`, desativar/remover override, troca de mapping principal.
- `findLatestAuthors(entity, ids, t)` → `Map<id, { user_id, user_name, date }>` (última entrada de cada id, uma query) — usado pra mostrar quem/quando confirmou um EAN físico.
- **Escopo atual**: Confirmar EAN físico, criar/alterar/apagar DE x PARA pelos fluxos manuais (`createForProduct`, `createFromUnmapped`, desativar/apagar override), criar/alterar (principal, código, integração)/apagar mapping de integração pelas rotas por produto, e a remoção do DE x PARA de outro produto quando alguém grava o EAN no produto (`ProductService.create/update` → `assertEanNotOwnedByAnotherProduct` com `audit`). Sync automático (`erp_data`, `gtin_erp`) **não** é auditado (ruído).
