# `reason_cancelled` + order status-sync helpers

`orders.reason_cancelled` (`m277`) — nullable enum (`OrderReasonCancelled`, `orders.types.ts`/`orders.model.ts`) that disambiguates WHY an order sits in `internal_status=CANCELLED`/situação `748772`. Full value list, and which of the 6 pipeline queues writes each one, lives in `../../modules/ml-order-pipeline/bug-fixes.md` (kept current there) and `docs/automation/order-pipeline.md`'s "Máquina de estados" section — not duplicated here.

## `escalateToHumanVerificationIfStillPending`/`syncOrderInternalStatus` (`order/helpers/order-status.ts`)

The shared, single decision point every queue must go through to either sync an order's status from a live Bling read or escalate it to human verification (situação `748772`), replacing what used to be separate ad-hoc PATCH-and-write logic per queue.

- `syncOrderInternalStatus(blingSituationId, orderId, reasonCancelled?)` — maps a raw Bling situação id; if it's already a *terminal* status (`COMPLETED_ORDER_INTERNAL_STATUSES` — `EMITTED`, `SENT_TO_TRANSPORTER`, `DELIVERED` — or `CANCELLED`), writes `internal_status`/`nfe_emitted` (and `reason_cancelled`, only for the cancelled case, only when the caller passed one) to match reality and reports `handled: true`. For any non-terminal status it does nothing and reports `handled: false` — the caller decides what to do next.
- `escalateToHumanVerificationIfStillPending({ idOrderSystem, blingApi, allowedPendingStatuses, reasonCancelled, beforeEscalate? })` — always re-reads the situação **live** from Bling first (never trusts a previous check, however recent) via `syncOrderInternalStatus`. Never escalates if the live status is already terminal (that call already synced the DB). If it's non-terminal but not one of the caller's own `allowedPendingStatuses` (e.g. `CNPJ_VERIFY_CNAE` only escalates from `OPEN`; `NFE_EMISSION` only from `WAITING_FOR_NFE_EMISSION`, because emission itself failed), it just syncs `internal_status` to the live value and does **not** escalate — the precondition the caller expected no longer holds, so escalating now would be based on stale reasoning. Only when both checks pass: runs the optional `beforeEscalate` hook (for a caller that needs to write its own note to Bling first), PATCHes situação to `748772`, and writes `internal_status: CANCELLED`, `nfe_emitted: false`, `reason_cancelled` to the given reason.
- `NFeQueue`'s NFe-emission 400 handling (`nfe.queue.ts`) is one concrete caller: a Bling `400` during `/gerar-nfe` is a business error, not transient, so instead of re-throwing (which used to exhaust BullMQ's 5 retries before finally reaching `onFailed` with the same message) it now calls `markOrderCancelled` directly with `OrderReasonCancelled.NFE_EMISSION_FAILED` and returns immediately.
- Both places that write `internal_status: CANCELLED` (the `syncOrderInternalStatus` branch and the end of `escalateToHumanVerificationIfStillPending`) also call `pdvSalesRequestService.cancelIfActiveByOrderId(orderId)` right after — a cancelled order takes any active `PdvSalesRequest` for it straight to `CANCELLED` (no-op if there isn't one, or if the request already finished/cancelled). See `.claude/entities/pdv-sales-request/index.md` — this is a different hook than `handleInvoiceCancelled` (invoice cancellation blocks in `INVOICE_CANCELLED` for a human decision; order cancellation goes straight to `CANCELLED` since there's nothing left to decide).

## `TERMINAL_ORDER_INTERNAL_STATUSES` (`orders.types.ts`)
Same terminal concept as above (`COMPLETED_ORDER_INTERNAL_STATUSES` + `CANCELLED`), exported as one combined constant for callers that just need "is this order still open/in-progress?" without caring which of the two. Only consumer so far: `NfeEmissionService.emitForOrder` (`bling-nfe/nfe-emission.service.ts`, used by the PDV module — see `../pdv-sales-request/index.md`) — the sole precondition for triggering a direct/manual NFe generation outside the ML automation pipeline (no store filter, no `situacao` gate, no field validation, unlike `NFeQueue`).
