# Orders summary endpoints (`GET /api/order/summary/...`)

Full detail (routing gotcha, per-endpoint definitions, `reason_cancelled` translation) lives in `../../modules/ml-order-pipeline/summary-endpoints.md`, since these endpoints are the primary Orders-side half of that pipeline's shipping logic. Facts specific to the underlying repository/model:

- **`shipTodayPendingWhere`'s `internal_status` guard was loosened — now only `CANCELLED` disqualifies an order from "pending today", not the full `COMPLETED_ORDER_INTERNAL_STATUSES` set.** An earlier revision (documented historically in `../../modules/ml-order-pipeline/summary-endpoints.md`) explicitly added a `NOT IN COMPLETED_ORDER_INTERNAL_STATUSES` guard as belt-and-suspenders against the `internal_status`/`batch_generated` divergence (`index.md`). The current code comment explains the reversal: what needs to be pending is the *invoice* (`batch_generated`/`status` on `InvoiceUnitBusinessAttributes`), not the order — `internal_status` can legitimately be `EMITTED`/`SENT_TO_TRANSPORTER`/`DELIVERED` while the invoice for *this specific* unit business still hasn't had its batch generated yet (the divergence is now treated as expected here, not guarded against). Only `CANCELLED` is excluded.
- **`shipToDefineWhere` now additionally requires `invoice_id IS NULL`.** Previously a `collection_date IS NULL` order with any status in `(OPEN, WAITING_CHANNEL_VALIDATION)` counted as "a definir" regardless of whether it already had an invoice. Now: once an order has a linked invoice, its shipping fate is already resolved by `shipTodayPendingWhere` (invoice in the 06h–14h window) or `futureShipmentWhere` (invoice emitted after the window) — no longer "to be defined" just because `collection_date` is null.
- **Orphan-invoice handling — Mercado Livre invoices with no linked `Order` are now counted directly by `OrderRepository`, not silently dropped.** `orphanInvoicePendingWhere(unitBusinessId)`/`orphanFutureInvoiceWhere()` (private methods on `OrderRepository`) query the `Invoice`/`Store` models **directly** (`Invoice.count`/`Invoice.findAll`, not via `invoiceService`/`invoiceRepository`) to find Mercado Livre notes never matched to an `Order`, adding them into `countShipTodayPending`/`countShipToFuture`/`groupShipToFutureByDate`/`findShipTodayPendingDetail` as extra rows alongside normal Order-based results (an orphan detail row has `number_order_system: null`, `customer_name` from the invoice's `receiver_name`, no `sale_date`/`collection_date` — `ShipTodayPendingDetailRow.number_order_system` widened to `string | null` for this). **This is a direct cross-entity model query from inside `OrderRepository`** — a deviation from this codebase's layer-separation rule (repository should go through another entity's repository, not its model directly; see root CLAUDE.md), worth knowing about if touched again, even though it's a data-completeness fix, not a scoping bug. `orphanFutureInvoiceWhere()`'s orphan count buckets into "tomorrow" specifically (`tomorrowBucketKey()`, `helpers/aggregates.ts`) since there's no `collection_date` to bucket by for a note with no order.
- **`countHumanVerification`/`groupHumanVerificationByReason` narrowed — `actual_situation = "748772"` alone is no longer sufficient.** Now also requires `internal_status = CANCELLED` AND `reason_cancelled IS NOT NULL`. A `748772` situação with no matching local cancelled+reasoned order no longer counts (can happen if the Bling situação changed again before a webhook confirmed the earlier state, or the local write that should have set `reason_cancelled` never completed).
- **`human_verification` is now also a `customField` on `OrderService.paginate()`** (`?filters[human_verification]=true` on the generic `GET /orders` listing, not just the summary count) — same 3 conditions (`internal_status: CANCELLED`, `actual_situation: "748772"`, `reason_cancelled: {Op.ne: null}`) as `countHumanVerification`, kept in sync by construction since both read the same 3 columns.
- **Shipping window redefinition (06h–14h, replacing the 13h-cutoff design)** — see `../invoice/ml-shipping-filters.md` for the full "why", the same redesign was applied to both files together. `OrderRepository.shippingWindowRange()` (private) and `invoice/helpers/custom-filters.ts`'s `shippingWindowRange()` are two separate copies of the identical function — a comment in each flags this as intentional-for-now ("se/quando virar utilitário compartilhado ... mover pra shared/utils/normalizers/date"), not yet deduplicated. `shipTodayPendingWhere`/`futureShipmentWhere` both key their cutoff behavior off `nowTz().isAfter(windowEnd)` (14h) exactly like the invoice side.
- **Maintenance script**: `src/scripts/bling/fix-by-different-situation.ts` replaced the older, interactive `fix-orders-by-status.ts` (deleted). Old script required the operator to already know/guess which Bling `situacao` ids were wrong and pick between two manual search modes before re-enqueueing `order.updated`/`order.created` jobs. New script paginates **every** order from Bling (`/pedidos/vendas`), maps each `situacao.id` via `mapOrderInternalStatus`, compares against the local `orders.actual_situation` for the matching `id_order_system`, and only re-enqueues (`BlingOrderQueue`, `order.updated`) the ones actually divergent — a direct, non-interactive reconciliation tool for the `internal_status`/`actual_situation` divergence (`index.md`). Supports `--data-inicial`/`--data-final` and `DRY_RUN=true`.
