# SupplierMapping (`src/modules/inventory/supplier-mapping/`)

- Table `product_supplier_maps`: `product_id`, `supplier_cnpj`, `supplier_product_code`, `integrations_id`, `is_physical_override` (`m326`, default false — "EAN físico confirmado", see `physical-ean-owner.md`; sync never creates it).
- Unique index `product_supplier_maps_integrations_id_code_unique (integrations_id, supplier_product_code)` since `m263` — replaced an older `(product_id, supplier_product_code)` unique that blocked the same code mapping to different products across different integrations (legitimate case).
- Trigger `trigger_prevent_supplier_mapping_gtin_conflict` (`m263`, narrowed `m265`): `supplier_product_code` can't equal another product's `ProductConfig.gtin` within the same integration (joins `unit_businesses.integrations_id`). No longer checks `gtin_package`.
- `supplierMappingService.findByProductCode(code, unitBusinessId)` — resolves `integrations_id` for the unit business then looks up the mapping. Reuse this instead of duplicating the `findOne`.
- `supplierMappingService.createFromUnmapped({ productId, unmappedInvoiceProductId, supplierCnpj?, userId? })` — `POST /supplier-mapping/from-unmapped`: links an `UnmappedInvoiceProduct` to an **already-existing** `Product`, without going through `InvoiceItems`. Controller checks `unmapped.integrations_id` against the caller's resolved integration first (404). Service rejects a non-`UNMAPPED` row ("já foi resolvido") and a non-existent product ("Produto não encontrado" — `internal_id` isn't an FK, would become an orphan mapping); `supplier_cnpj` normalized/validated. Returns `CreateFromUnmappedResult` `{ supplierMapping | null, integrationMapping {id, external_id, is_primary} | null, integration {id, name}, integrationMappings[] }` — the last one is `integrationMappingService.findProductMappingsInIntegration` (all of the product's mappings in that integration, `erp_data` reduced to `{name, ean}`); front warns when `length > 1`.
  - Branch on whether the product already has an `integration_mapping` in the unmapped's integration (`findExternalIdsMap`):
  - **Already mapped** (old flow): code = `unmapped.ean ?? unmapped.sku`, `assertEanFreeForProduct`, then SupplierMapping **always `is_physical_override: true`** (existing same-product row is marked; other product → error). Any error propagates. If `external_id` is set, `createOrUpdateIntegrationMapping` too (may be born non-primary). Unmapped row deleted in the transaction.
  - **Not mapped** — only `type ERROR_CATALOG` with reason `UNMAPPED_REASON_NEW_CATALOG_PRODUCT` / `UNMAPPED_REASON_INVOICE_PRODUCT_NOT_IN_DB` (constants in `unmapped-invoice-product.types.ts`, also used where the rows are created) **and** `external_id`; otherwise `SupplierMappingError PRODUCT_NOT_MAPPED_IN_INTEGRATION` with a lay message per reason (front only shows `error`). Creates the integration mapping (primary only if the product has none there — never swaps the primary; manual via `PUT /integration-mapping/product/:productId/:id`), audited (INTEGRATION_MAPPING + PRODUCT). SupplierMapping is tried inside a **savepoint** (`sequelize.transaction({ transaction: t })`) — data/rule failures (EAN in use, override, no EAN/SKU, trigger) are logged and swallowed, `supplierMapping: null`; `ConnectionError`/`TimeoutError` still abort. After commit, `unmappedInvoiceProductService.resolveFromCreatedProduct` closes every UNMAPPED row of that `external_id` (invoice rows get the `InvoiceItem` + batch/PDV sync) instead of a bare delete; a failure there is only logged (the link is already committed).
  - `external_id` already pointing at **another** product → error + rollback in every branch (already mapped, not mapped, `ERROR_CATALOG_DUPLICATE`) — never closes the row silently.
  - `ERROR_CATALOG_DUPLICATE`: ambiguous code — only the integration mapping (no SupplierMapping, no not-mapped gate), row deleted, link audited; requires `external_id`.
- Product-scoped CRUD, always scoped to `product_id` (route) + caller's resolved `integrations_id` (same tenant scope as `index`; body `product_id`/`integrations_id` ignored):
  - `GET /supplier-mapping/product/:productId` → `findByProductId`: paginated via `repository.findPaginated` forced where.
  - `POST /supplier-mapping/product/:productId` → `createForProduct` (body `supplier_product_code`, `supplier_cnpj?`): code normalized by `normalizeSupplierCode` (String + trim, blank → 400) and CNPJ by `normalizeSupplierCnpj` (digits, `isValidCNPJ`, empty → null); pre-checks `PRODUCT_NOT_MAPPED_IN_INTEGRATION`, then **inside the transaction** `lockEanInIntegration` (`pg_advisory_xact_lock` on integration + `eanZeroInsensitiveKey`, also used by `updateForProduct`, `assignPhysicalOwner` and the from-unmapped savepoint — serializes writes of the same EAN family so two concurrent writes can't both pass the owner check) + `EAN_HAS_PHYSICAL_OVERRIDE` / `EAN_OWNED_BY_ANOTHER_PRODUCT` (with `owners`), then `create`; closes the EAN's `ERROR_SCAN` rows and audits. FK error → "Produto não encontrado".
  - `POST /supplier-mapping/product/:productId/physical-owner` → `assignPhysicalOwner` — see `physical-ean-owner.md`.
  - `PUT /supplier-mapping/product/:productId/:id` → `updateForProduct`: only sent fields; uses `repository.update` (instance) so `beforeUpdate` CNPJ-cleaning hook runs. 404 if not that product/integration. Override row: only admin/developer; code change is pre-checked. `is_physical_override: false` deactivates the override (audited, see `physical-ean-owner.md`); `true` → error.
  - `DELETE /supplier-mapping/product/:productId/:id` → `deleteForProduct`: single `bulkDelete` with scoped where; 404 if 0 rows. Override row: only admin/developer, audited.
  - Generic routes drop `is_physical_override` from the body. `POST /` delegates to `createForProduct` (body `product_id`). `POST /bulk` normalizes code/CNPJ and checks product-in-integration + EAN per item. `PUT /:id` normalizes code/CNPJ, re-checks the EAN and, when `product_id` changes, that the new product is linked to the integration. `PUT /bulk` is unreachable (`PUT /:id` registered first in `BaseController` — left as is: reordering would enable the unscoped generic `bulkUpdate` on every controller). Ids in routes/body validated with `assertUuid`.
  - `bling-direct-upsert` (`product_supplier_maps` job): skips non-primary Bling codes; only reuses the row it created (`supplier_cnpj = PENDING-<supplierBlingId>`, non-override) — never repoints a DE x PARA made by a person; same code already on the product → no-op. The marker prefix is `SYNC_SUPPLIER_CNPJ_PREFIX` (`supplier-mapping.types.ts`): the model's `beforeCreate`/`beforeUpdate` hooks skip CNPJ cleaning for it (before, `create` stored only the digits, so the reuse lookup never matched rows the sync created). On edit (`updateForProduct` / `PUT /:id`), `normalizeSupplierCnpj(value, current)` keeps the marker when the screen sends back only its digits (the front strips non-digits); any other value is validated as CNPJ.
  - `/add/item` (`invoice-items`) runs `assertEanFreeForProduct` before creating the mapping; controller returns `code`.
- `GET /supplier-mapping/integration-pending/get` — see `../../modules/integration-pending-report.md`.
