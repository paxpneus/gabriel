# Tecinco catalog-duplicate pre-flight (`migrateProdutos`, `tecinco-migration.runner.ts`)

Tecinco reuses/duplicates codes (`epctb_codigofabrica`/`epctb_coded`/`epctb_ean`) across unrelated catalog entries — confirmed real cross-maps in prod (e.g. a `12-16.5` skid-steer tire and a `265/60R18` Bridgestone Dueler both via `sku=48681`). This pre-flight runs before `migrateProdutos` (called by the full-migration script and `TCarSyncQueue`'s incremental sync, same `runMigration` entry point either way) enqueues anything onto `processProduct`. See `automap-cascade.md` for the fallback this protects.

1. Fetches the Tecinco catalog **in full** — every tire group (`tecincoTireGrupoIds`), ignoring this run's `grupos` filter and `alteradoDesde` (a collision can involve a product outside this run's own batch) — via `fetchTecincoCatalog` (extracted from `dump-tecinco-catalog.ts`, whose own `main()` is `require.main === module`-guarded so importing elsewhere doesn't trigger it). Still scoped to this run's `branchIds` (a collision only matters for branches actually being synced).
2. Writes the catalog to `CATALOG_OUTPUT_PATH` as a pure intermediate artifact — deleted right after building the in-memory index, and any pre-existing file at that path deleted first too (defensive against a prior crashed run). **Known unaddressed gap**: concurrent `migrateProdutos` runs would race on this file path — not worth a unique-per-run filename unless actually observed.
3. Builds 2 `Set<string>` (`buildTecincoDuplicateValueSets`) of **values** (not product ids) appearing on more than one catalog entry: one for `sku` (`effectiveSku` = `epctb_codigofabrica`, falling back to `epctb_coded` only when there's no código de fábrica at all), one for `ean`. `epctb_coded` was originally its own axis, collapsed into `sku` since código de fábrica is what the cascade actually reads. A value repeated 2x or 200x is equally unsafe to auto-map on — no "too common to be a real collision" exemption (that reasoning is backwards). Empty/null values and EAN's "sem GTIN" placeholder variants (`normalizeEan`) are never counted — confirmed against a real prod catalog dump that non-placeholder-looking repeats (e.g. `sku=48681` ×64) are exactly the dangerous case, not noise.
4. Batch-checks which `external_id`s already have a **valid** (non-orphaned — `internal_id` pointing at a `Product` that actually exists) `integration_mapping`, via `integrationMappingService.findValidExternalIdsSet(integrationsId)` — queries its own model with a plain `where`, then calls `productService.findAll` for existence (two services, no cross-model query in either repository, per the layering rule in root CLAUDE.md).
5. Always enqueues every catalog item — never skips one for being duplicated (an earlier design that skipped `enqueue()` and wrote `registerCatalogDuplicate` instead no longer exists). `findTecincoCollidingFields` runs unconditionally for every item (cheap — just `Set` lookups) and sets `skuDuplicated`/`eanDuplicated` on the job payload (`TCarUpsertJobPayload`); the item is **always** enqueued regardless. `processProduct` decides what to do with the flags.
6. **`processProduct` (`tecinco-api-fetch.queue.ts`)** reads `opts.skuDuplicated`/`opts.eanDuplicated` (plumbed through `TCarUpsertQueue.process`'s job-data → opts mapping) → `isDuplicatedInCatalog = skuDuplicated || eanDuplicated`:
   - **Fallback gate**: `autoMapExistingProductBySku` is skipped entirely when `isDuplicatedInCatalog` — never auto-map on an ambiguous code, decided per-job instead of at enqueue time. Also skipped unconditionally when `opts.create` is true (manual creation never reuses an existing product via fallback).
   - **Unmapped registration**: when nothing resolves (`opts.create` false, mapping + fallback empty-handed), `UnmappedInvoiceProduct.type` = `"ERROR_CATALOG_DUPLICATE"` when `isDuplicatedInCatalog`, else `"ERROR_CATALOG"` — both share the exact same upsert-by-`external_id`/`ean` path, just a computed `type`/`reason`. Self-healing for free: every item is always enqueued and the upsert re-evaluates `type`/`reason` each pass, so a code that stops colliding flips the row back to `ERROR_CATALOG` (or deletes it if it now resolves) on the next sync — no separate cleanup step.
   - **`skuOmitted`/`eanOmitted`** (declared `let`, seeded from the two opts flags **before** `resolveProductWithMapping` is called — order matters, see `duplicate-protection.md`'s production bug): the single mechanism deciding everywhere downstream (product creation, per-filial `ProductConfig.upsert`, both `ensureSupplierMappings` calls) whether `sku`/`gtin` get written at all. Can also be set independently by the live `isCodeOwnedByAnotherProduct` check in the `opts.create` branch (`duplicate-protection.md`) — both triggers converge on the same downstream behavior: never block, just omit the field.
7. **`UnmappedInvoiceProduct.sku` stores the display code, not the dedup key** (applies to `processProduct`'s own unmapped branch and `ensureProductsFromInvoiceItems`'s "produto não encontrado" branch): written as `codigoFabrica ?? epctb_coded ?? null` (same `effectiveSku` rule as duplicate detection) — purely for human review, **not** used to find/dedupe the row. Dedup keys off `external_id` (`epctb_codigo`, the ERP's own stable id) wherever available. This now includes `ensureProductsFromInvoiceItems`'s `invoice_id`-scoped rows too: since that function resolves strictly via `integration_mapping` (see below), `systemId` is always known for the item, so it's written as `external_id` on the unmapped row even though `invoice_id` is set — no longer the `sku`-only exception it used to be. `invoice-xml.ts`'s own per-invoice reconciliation loop still keys its `ean`/`sku` dedup off the item itself (unrelated to `external_id`), but `external_id` is what lets `unmappedInvoiceProductService.resolveFromCreatedProduct` find and close this row later from the catalog side (see `create-flow.md`). `InvoiceOperationalItemFromXml.sku` (resolved items, not unmapped) deliberately left untouched — still carries `systemId`, matched against the NF-e XML's own `cProd` in `findXmlItemForOperationalItem`, an unrelated concern.

Reprocessing an invoice that arrived before its product existed self-heals independently of all this: `invoiceService.addMissingInvoiceItems` + the stale-unmapped-row cleanup loop (`invoice-xml.ts`, `bling-api-fetch.queue.ts`) already create the real `InvoiceItems` and delete the obsolete unmapped row.

## `ensureProductsFromInvoiceItems` — fallback removed entirely (invoice resolution, not catalog sync)

Real prod incident (2026-09): `codigoFabrica=14X40MA` (42x collision in the catalog, see `automap-cascade.md`) resolved correctly via `integration_mapping` (stable systemId) for an invoice item, but `ensureSupplierMappings` then failed trying to register the mapping because the code already belonged to a different product — `SupplierMappingConflictError`, CRITICAL alert, invoice not aborted. Investigating this revealed the `isDuplicatedInCatalog` gate above only protected `processProduct` (catalog sync); `ensureProductsFromInvoiceItems` (`tecinco-api-fetch.queue.ts`) called `resolveProductBySupplierMapping` unconditionally whenever there was no `integration_mapping` yet — no duplicate check, so this fallback could **silently** return the wrong product (no error, no alert), unlike the mapping-write path which at least fails loudly.

**First fix (superseded)**: `ensureProductsFromInvoiceItems` was made to consult the same duplicate index as the preflight, via `getCachedTecincoDuplicateValueSets`/`findTecincoCollidingFields`, before attempting the `SupplierMapping` fallback — duplicated code skipped the fallback and produced a distinct "duplicated, needs review" unmapped reason instead of risking a wrong link.

**Current state**: the `SupplierMapping` fallback (and the `ensureSupplierMappings` backfill call that used to follow a resolved product) were removed from `ensureProductsFromInvoiceItems` entirely, closing the whole incident class at the root instead of gating it. Resolution there is now strictly `integration_mapping`-only: no match → `UnmappedInvoiceItemFromXml` with `type: "ERROR_CATALOG"` and `external_id: systemId` set, no fallback attempt of any kind. The duplicate-catalog distinction no longer applies to this function — a duplicated code and a genuinely-unknown code look identical here (both just "no `integration_mapping` yet"), since neither ever reaches a fallback that could be ambiguous.

**`getCachedTecincoDuplicateValueSets` now has no reader.** `ensureProductsFromInvoiceItems` was its only call site; `tecinco-migration.runner.ts` still calls `setCachedTecincoDuplicateValueSets` (write side, feeds `processProduct`'s own `skuDuplicated`/`eanDuplicated` job-payload flags via a separate path, not this cache) but nothing reads the cache back anymore. The TTL/in-flight-promise-map machinery described below is dead weight until/unless something reads it again — flagged here, not removed, since cleaning up `tecinco-duplicate-detection.ts` wasn't part of this change.

**Known limitation (historical, from the first fix)**: neither fix retroactively corrects `InvoiceItems`/`InvoiceFiscalItem` rows already created with a wrong `product_id` from the old unconditional-fallback behavior — `product_id` is written directly on the row with no reference back to the `SupplierMapping` that produced it. Reconciling history would require a manual audit (cross-referencing each historically-duplicated `codigoFabrica` against `InvoiceItems.product_id` and creation date) — not implemented.

Cache mechanics kept for reference (now dormant): the catalog sync preflight fetches the **fresh** catalog every run; `getCachedTecincoDuplicateValueSets` cached the index per `branchIds` with a TTL (`TCAR_DUPLICATE_CACHE_TTL_MS` env var, default 30min) plus an in-flight promise map (`inFlight` in `tecinco-duplicate-detection.ts`) to prevent concurrent cache-miss stampedes — both only mattered while `ensureProductsFromInvoiceItems` read from it per invoice.
