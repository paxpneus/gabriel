# Invoice entity (fiscal)

`src/modules/warehouse/fiscal/invoices/`

- `invoice/` — `Invoice` model/service/repository/controller + `invoice-label.service.ts` (EAN for printed labels) + `helpers/totals.ts` (`totalExpectedLiteral`/`totalReadLiteral`).
- `invoice-items/` — `InvoiceItems`; resolves product/config per line — see `item-resolution.md`.
- `InvoiceFiscalItem` — sibling model, own `invoice-fiscal-item/` folder, **no repository/service/controller of its own** (just `.model.ts`/`.types.ts`) — queried/written directly wherever needed (`invoice.repository.ts`, `invoice.service.ts`, `invoice-items.service.ts`). Same accepted no-layer exception applies to `SalesOrderItemSnapshot`/`KitComponent` reads in this module (see `supplier-discount/report-value.md`).

Split by subject:
- `item-resolution.md` — product/config resolution order, unmapped-product reconciliation cascade, related bug fixes
- `ml-shipping-filters.md` — Mercado Livre shipping-queue filters
- `supplier-discount/filter.md` — `rim`/`supplier_discount` invoice filters
- `supplier-discount/report-value.md` — per-line discount value/rule in reports

## Misc fixes/filters
- **New `transporterStatus` filter on `listInvoices`** — `?filters[transporterStatus]=pending-<transporterId>` (`InvoiceRepository.extractTransporterStatusFilter`). Filters `unitBusinessAttributes.status IN (PENDING, OPEN)`, `batch_generated = false`, `Invoice.transporter_id = <transporterId>`, and excludes Mercado Livre notes (`store.name != "MercadoLivre"`, `store` include becomes `required: true` with that `where` only when this filter is active). Meant to open the invoice listing pre-filtered from a `pending_batch_by_transporter` card click (`OrderService.getOrdersStatusSummary`, `.claude/entities/order/summary-endpoints.md`) — only `pending-` prefix is parsed today, no other status prefix implemented.
- **`processStatus` filter replaced the old boolean `pendingProcess`** (`invoice.service.ts`/`invoice.repository.ts`) — now 3-value: `pendingProcess` (`status NOT IN (FINISHED, CANCELLED)`, status-only now — the old version also OR'd in `batch_generated = false`, that's gone), `finishedProcess` (`batch_generated = true AND status IN (FINISHED, CANCELLED)` — `printed_label = true` dropped, no longer required), `notStartedProcess` (new — `status IN (OPEN, PENDING) AND batch_generated = false`).
- `InvoiceRepository.listInvoices`'s attribute exclude list now also drops `xml_path` (alongside `source_payload`) from the paginated listing response.
- **Fixed — `getInvoiceProductReport`'s "default seller" fallback pointed at a dead hardcoded UUID.** Was `userService.findById(default_seller)` (module-level constant `"5ff76374-4d67-4ef3-a566-349a015f86b1"`, stopped resolving). Now `userService.findOne({ where: { name: "Rafael Minetto" } })` — the constant is still declared but unused.
- **Fixed — `getFullInvoiceForAllUnits` crash on Bling notes without `chaveAcesso` yet**: `fetchAndUpsertInvoice` looked up the pre-existing invoice by `xml_key` only. A note pending SEFAZ authorization (`situacao: 1`) has no `chaveAcesso`, so the lookup args were both `undefined` and the repository's own guard threw — crashing every retry forever even though the note already existed in the DB under `id_system = String(nf.id)`. Fixed: `getFullInvoiceForAllUnits(invoiceId?, invoiceKey?, idSystem?)` now also matches by `id_system` when no `invoiceId` is given; Bling passes `String(nf.id)`. `invoice-xml.ts`'s own `findByIdFullForAllUnits` call (Tecinco/manual XML import) unchanged — that flow always has a `chaveAcesso`.
- **Transporter resolution during invoice import is centralized in `TransporterService`** (`src/modules/warehouse/transporter/transporter.service.ts`) — both `bling-api-fetch.queue.ts`'s `fetchAndUpsertInvoice` and `invoice-xml.ts`'s `upsertInvoiceFromXml` (Tecinco) just call `transporterService.resolveTransporter({ document, name, city, uf, integrationsId })`; neither file owns transporter-lookup/creation logic of its own anymore (no direct `Transporter.findOne`/`.create`, no local `NO_TRANSPORTER_*`/`ENTREGA_PROPRIA_*` constants).
  - `resolveTransporter` branches on `document`/`name`: no document and `name` matches `"Entrega Própria"` (case-insensitive) → `getOrCreatePlaceholderByName("Entrega Própria", "0000000000", ...)` — Bling's own delivery, not a missing-transporter case, so it gets its own sentinel document distinct from the generic placeholder. No document otherwise (or it cleans to the sentinel `"0000000"`) → `getOrCreateNoTransporterPlaceholder` (same helper, `"Sem transporte"`/`"0000000"`), using `city`/`uf` only on first creation. A real document → `findOrCreateByDocument({ document, name, city, uf, integrationsId })`: look up local `Transporter.cnpj`; if not found, register a new row using whatever `name`/`city`/`uf` the caller passed in (falling back to the document itself as `name` if none given) — `integrations_id` is the caller's own integration (Bling or Tecinco).
  - **CNPJ-registry lookup (openCNPJ/BrasilAPI via `fetchCNPJ`, `src/modules/handlers/cnpj/api/cpnj_api.service.ts`) is intentionally not wired into transporter creation right now** — it was tried in an earlier iteration of `findOrCreateByDocument` but was pulled back out at the user's request; new transporters are registered with whatever name/city/uf the NF-e's own source (API or XML) already carried, not looked up against the official registry. `fetchCNPJ` itself is untouched and still used elsewhere (`cnpj` queue) if this gets revisited later.
  - **Document/name source priority differs per integration, matching where each API actually puts the data.** Bling: its own invoice detail (`nf.transporte.transportador.numeroDocumento`/`.nome`) is tried first; only when Bling returns no document does the code keep whatever `extractPartiesFromXml` (NF-e's `transp.transporta.CNPJ`/`.xNome`/`.xMun`/`.UF`) already extracted from the XML (except the `"Entrega Própria"` case, which explicitly discards the XML document even when Bling's own field is empty). Tecinco's own API never returns transporter data at all, so its XML (same `transp.transporta` shape) is unconditionally the only source. In both files, `invoiceBaseData.transporter_document`/`.transporter_name` are read back from the *resolved* `Transporter` row (`transporter?.cnpj`/`transporter?.name`) rather than the raw extracted values, so the invoice's display columns always match whatever the linked `transporter_id` actually points to.

## Auth
`invoice.controller.ts` has HIGH-severity scoping gaps — see `../../modules/auth.md`. Not fixed: `show`/`destroy`/`create` unscoped; other actions trust a client-supplied `?unitBusinessId=` over the logged user's own; DANFE/XML batch downloads have no store filter.

## `danfe_path` — now actually populated
`invoices.danfe_path` existed as a column but was always written as `""` (dead field) until the PDV Management module needed it. Now populated on create, never touched on update (a note's fiscal content doesn't change after emission, so there's no reason to redo this per re-sync):
- **Bling**: the API already returns a rendered PDF — `BlingApiInvoice.linkPDF` (typed, was previously unused). `bling-api-fetch.queue.ts::fetchAndUpsertInvoice` downloads it (same `fetch()` pattern already used for `nf.xml`) and uploads the buffer via `uploaderService` (`/danfes` directory) — no PDF generation involved.
- **Tecinco**: no rendered PDF comes from the API, only XML — `invoice-xml.ts::upsertInvoiceFromXml` generates it from `xmlContent` via `generateDanfePdfBuffer` (`src/shared/utils/xml/danfe-generator.ts`, extracted from `invoice.controller.ts::getDanfeBatch`'s pre-existing `gerarPDF`/`PassThrough` logic — that endpoint now calls the same shared helper instead of duplicating it) and uploads it the same way. Only runs in the `!existingInvoice` (create) branch.
- Both paths reuse `uploaderService.upload({..., directory: "/danfes", preserveFilename: true})` (WebDAV storage, `src/modules/handlers/uploader/`).

## Provisional/"stub" invoices (`InvoiceService.createStub`) and the 3 shapes of `danfe_path`

Two callers need to link an `invoice_id` FAST (HTTP request path), before the real note is fully known — the slow real import (this file's "`danfe_path` — now actually populated" section above, or the PDV Tecinco XML pipeline) always runs later, in background, and updates the SAME row (matched by `xml_key`/`id_system`, never creates a second row for the same note):
- `bling-order.service.ts::resolveInvoiceId` — order payload already carries `notaFiscal.id` before the `invoice`/`consumer_invoice` webhook finishes; fetches just `GET /nfe/:id` (one call) and links a stub instead of leaving `order.invoice_id` null until the full webhook lands.
- `pdv-sales-request.service.ts::attachTransferInvoice` (`danfeBuffer` branch) — see `.claude/entities/pdv-sales-request/index.md`.

`InvoiceService.createStub({ id?, integrationsId, numberSystem, idSystem?, xmlKey?, danfePath?, senderCnpj?, senderName? })` fills only what the caller already has; every other NOT NULL column (`customer_name`, `customer_document`, `sender_cnpj`/`sender_name` when not given, `receiver_cnpj`, `receiver_name`) gets `""`, never a caller-invented placeholder word. `store_id` always resolves to the `Store` named `"Outros"` via `storeService.findOne` (never `findOrCreate` — throws a clear error if that row is missing, instead of writing an invalid `store_id`). Because it's a plain `this.create(...)` (inherited `BaseService.create`, not `createWithRelations`), a stub row gets **no** `InvoiceUnitBusinessAttributes` and **no** "Nova nota fiscal recebida" notification at creation time.

**Fixed — stub row stayed WITHOUT `InvoiceUnitBusinessAttributes` forever, even after the real background import fully enriched it.** The real import (`invoice-xml.ts`'s `upsertInvoiceFromXml` for Tecinco, `bling-api-fetch.queue.ts`'s `fetchAndUpsertInvoice` for Bling) matches the stub by `xml_key`/`id_system` and always takes the **UPDATE** branch (`updateInvoicesForAllUnitBusiness`) — `InvoiceUnitBusinessAttributes` rows are only ever created by the **CREATE** branch (`createWithRelations`), so a stub-originated invoice, once "found" instead of "created", never got them at all, no matter how many times it was resynced. This broke anything that reads `unitBusinessAttributes.status` for that invoice (status-driven listings/filters, `invoice.controller.ts`'s `status`/`type` custom fields, batch generation eligibility). **Fixed** with `InvoiceService.ensureUnitBusinessAttributes(invoiceId, { senderCnpj?, receiverCnpj?, initialStatus?, invoiceType?, transaction? })` — same sender/receiver-CNPJ→UnitBusiness resolution as `createWithRelations`'s own inline logic (not extracted into a shared helper, to avoid touching that already-tested code path), but idempotent: checks `findInvoiceAttribute` per resolved side before inserting, so calling it on an invoice that already has attributes (the normal case, always true for non-stub invoices) is a no-op. Called from both `invoice-xml.ts` and `bling-api-fetch.queue.ts`'s UPDATE branches, right after `updateInvoicesForAllUnitBusiness`, unconditionally (cheap enough, and self-heals if this ever regresses again) — not only when the invoice is known to be stub-originated.

`danfe_path` now has 3 possible shapes, all handled by `getDanfeBuffer`:
1. **Internal, finalized** (the pre-existing case documented above) — `uploaderService.getFile(path)`.
2. **`temp://<tempFileId>` sentinel** — set by `attachTransferInvoice` when staging the DANFE the PDV user just uploaded (`tempFileService.create` + `uploaderQueue.enqueueUpload(..., "INVOICE_DANFE")`, same instant-response pattern as `PDV_SALES_REQUEST_RECEIPT`). `getDanfeBuffer` reads the raw buffer straight from `temp_files` while it's still in staging, with a race fallback (upload finished between the check and now) that reloads and serves via `uploaderService`. `FINALIZE_CHECKERS.INVOICE_DANFE` (`uploader-finalizers.ts`) had to learn to treat this sentinel as "still pending" — it used to be a bare truthiness check (`danfe_path` accepts `NULL`, so any non-null value meant "already uploaded"), which would have made the reconcile sweep delete the still-in-flight `temp_files` row out from under the async upload the moment a stub set a non-null placeholder.
3. **Raw external URL** (`http...`) — set directly by `bling-order.service.ts::resolveInvoiceId` from Bling's own `linkPDF`, no download involved (that's the whole point of the fast path). `getDanfeBuffer` fetches it directly via `fetch()`, **never through `uploaderService`** — `uploaderService`'s axios client (`uploaderApi`) attaches a hardcoded Basic-Auth header for the internal storage backend to every request it makes, absolute URL or not, so routing an external URL through it would leak that credential to the third-party host. This guard didn't exist before because `danfe_path` never held an external URL prior to this stub feature.

## Cancellation hook into PDV Management
When `upsertInvoiceFromXml` detects `cancelledInvoice` (its own existing `isCancelledInvoice` check, unchanged) or `bling-api-fetch.queue.ts` sees `nf.situacao === 2` on an update, both now call `pdvSalesRequestService.handleInvoiceCancelled(invoice.id)` after the invoice upsert finishes — see `.claude/entities/pdv-sales-request/index.md`. This is the only place invoice cancellation is currently surfaced to another module; it does not change any invoice-side behavior (still sets `invoice_unit_business_attributes.status = PENDING_CANCELLED_SYSTEM`, same as before).
