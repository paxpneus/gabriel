## Misc fixes/filters
- **New `transporterStatus` filter on `listInvoices`** — `?filters[transporterStatus]=pending-<transporterId>` (`InvoiceRepository.extractTransporterStatusFilter`). Filters `unitBusinessAttributes.status IN (PENDING, OPEN)`, `batch_generated = false`, `Invoice.transporter_id = <transporterId>`, and excludes Mercado Livre notes (`store.name != "MercadoLivre"`, `store` include becomes `required: true` with that `where` only when this filter is active). Meant to open the invoice listing pre-filtered from a `pending_batch_by_transporter` card click (`OrderService.getOrdersStatusSummary`, `.claude/entities/order/summary-endpoints.md`) — only `pending-` prefix is parsed today, no other status prefix implemented.
- **`processStatus` filter replaced the old boolean `pendingProcess`** (`invoice.service.ts`/`invoice.repository.ts`) — now 3-value: `pendingProcess` (`status NOT IN (FINISHED, CANCELLED)`, status-only now — the old version also OR'd in `batch_generated = false`, that's gone), `finishedProcess` (`batch_generated = true AND status IN (FINISHED, CANCELLED)` — `printed_label = true` dropped, no longer required), `notStartedProcess` (new — `status IN (OPEN, PENDING) AND batch_generated = false`).
- `InvoiceRepository.listInvoices`'s attribute exclude list now also drops `xml_path` (alongside `source_payload`) from the paginated listing response.
- **Fixed — `getInvoiceProductReport`'s "default seller" fallback pointed at a dead hardcoded UUID.** Was `userService.findById(default_seller)` (module-level constant `"5ff76374-4d67-4ef3-a566-349a015f86b1"`, stopped resolving). Now `userService.findOne({ where: { name: "Rafael Minetto" } })` — the constant is still declared but unused.
- **`getFullInvoiceForAllUnits(invoiceId?, invoiceKey?, idSystem?)`** (`invoice.repository.ts`): with no `invoiceId`, matches by `xml_key` first — a hit there is always the same real note, since `chaveAcesso` is a SEFAZ-issued key, identical across every integration that reads the same NF-e — and returns it immediately. Only falls back to `id_system` when `xml_key` finds nothing (covers Bling notes pending SEFAZ authorization, `situacao: 1`, which have no `chaveAcesso` yet), and even then only accepts that row if its own `xml_key` is null or equal to the `invoiceKey` being searched for — a row whose `xml_key` already points to a different note is never treated as a match. This replaced a plain `Op.or` between the two fields, which could return an `id_system`-matched stub whose `xml_key` differed from (or was still empty for) the note actually being upserted; the UPDATE that followed then tried to overwrite that stub's `xml_key`, colliding with `invoices_xml_key` on the different row that legitimately owned it. `invoice-xml.ts`'s own `findByIdFullForAllUnits` call (Tecinco/manual XML import) is unaffected — that flow always has a `chaveAcesso`.
- **Transporter resolution during invoice import is centralized in `TransporterService`** (`src/modules/warehouse/transporter/transporter.service.ts`) — both `bling-api-fetch.queue.ts`'s `fetchAndUpsertInvoice` and `invoice-xml.ts`'s `upsertInvoiceFromXml` (Tecinco) just call `transporterService.resolveTransporter({ document, name, city, uf, integrationsId })`; neither file owns transporter-lookup/creation logic of its own anymore (no direct `Transporter.findOne`/`.create`, no local `NO_TRANSPORTER_*`/`ENTREGA_PROPRIA_*` constants).
  - `resolveTransporter` branches on `document`/`name`: no document and `name` matches `"Entrega Própria"` (case-insensitive) → `getOrCreatePlaceholderByName("Entrega Própria", "0000000000", ...)` — Bling's own delivery, not a missing-transporter case, so it gets its own sentinel document distinct from the generic placeholder. No document otherwise (or it cleans to the sentinel `"0000000"`) → `getOrCreateNoTransporterPlaceholder` (same helper, `"Sem transporte"`/`"0000000"`), using `city`/`uf` only on first creation. A real document → `findOrCreateByDocument({ document, name, city, uf, integrationsId })`: look up local `Transporter.cnpj`; if not found, register a new row using whatever `name`/`city`/`uf` the caller passed in (falling back to the document itself as `name` if none given) — `integrations_id` is the caller's own integration (Bling or Tecinco).
  - **CNPJ-registry lookup (openCNPJ/BrasilAPI via `fetchCNPJ`, `src/modules/handlers/cnpj/api/cpnj_api.service.ts`) is intentionally not wired into transporter creation right now** — it was tried in an earlier iteration of `findOrCreateByDocument` but was pulled back out at the user's request; new transporters are registered with whatever name/city/uf the NF-e's own source (API or XML) already carried, not looked up against the official registry. `fetchCNPJ` itself is untouched and still used elsewhere (`cnpj` queue) if this gets revisited later.
  - **Document/name source priority differs per integration, matching where each API actually puts the data.** Bling: its own invoice detail (`nf.transporte.transportador.numeroDocumento`/`.nome`) is tried first; only when Bling returns no document does the code keep whatever `extractPartiesFromXml` (NF-e's `transp.transporta.CNPJ`/`.xNome`/`.xMun`/`.UF`) already extracted from the XML (except the `"Entrega Própria"` case, which explicitly discards the XML document even when Bling's own field is empty). Tecinco's own API never returns transporter data at all, so its XML (same `transp.transporta` shape) is unconditionally the only source. In both files, `invoiceBaseData.transporter_document`/`.transporter_name` are read back from the *resolved* `Transporter` row (`transporter?.cnpj`/`transporter?.name`) rather than the raw extracted values, so the invoice's display columns always match whatever the linked `transporter_id` actually points to.

## `GET /invoice/transfer/list` — notas de transferência

Mesma listagem paginada de `GET /invoice` (`listInvoices`/`InvoiceRepository.listInvoices`), restrita a notas "de transferência": remetente E destinatário são ambos `unit_businesses` próprias, não um cliente/fornecedor externo. Não existe flag/tipo próprio pra isso na nota — resolvido comparando `sender_cnpj`/`receiver_cnpj` contra o conjunto de CNPJs cadastrados em `unit_businesses` (`InvoiceRepository.findAllUnitBusinessCnpjs`), aplicado como `sender_cnpj IN (...) AND receiver_cnpj IN (...)` (`forcedWhere` do `findPaginated`).

`unit_business_id` é **opcional** aqui (lido via `InvoiceController.extractUnitBusinessIdFromRequest`, mesma leitura dupla — `?unitBusinessId=`/`filters[unit_business_id]` — de `resolveUnitBusinessId`, mas **sem** cair no `unitBusinessId` do usuário logado quando ausente): se o front não mandar nada, lista transferências de todas as unit businesses, sem escopar. Quando ausente, o join de `unitBusinessAttributes` (status/type/batch_generated por loja) e o de `batchInvoice.batch` deixam de ser `required`/escopados por `unit_business_id` — só viram filtro de verdade se algum outro filtro (status/type/batch_generated/processStatus/transporterStatus) for informado; `total_read` (`helpers/totals.ts#totalReadLiteral`, agora com `unitBusinessId` opcional) soma leitura de todas as lojas nesse caso, não de uma só.

`InvoiceRepository.listInvoices`/`listTransferInvoices`/`findAllTransferInvoices` compartilham a montagem de includes/attributes (`buildListedInvoiceQueryOptions`) e o mapeamento de linha (`mapListedInvoice`) — a única diferença de verdade entre elas é o `forcedWhere`/uso de `findPaginated` vs. `model.findAll` direto.

### `GET /invoice/report/transfer` — mesmo filtro, sem paginação

Relatório de exportação: mesmos filtros/mesma linha por nota de `listTransferInvoices` (`InvoiceRepository.findAllTransferInvoices`/`InvoiceService.getTransferInvoicesReport`), só que devolve tudo que bate no filtro de uma vez (`{ data: [...] }`), sem `page`/`perPage`. Não dá pra usar `BaseRepository.findPaginated`/`findAll` genéricos aqui — o primeiro sempre pagina, o segundo sobrescreve `where` com só o que o `QueryParser` resolve (sem como combinar com o `forcedWhere` de CNPJ) — por isso monta a query direto contra `this.model`, replicando manualmente a combinação `resolved.where + forcedWhere` que `findPaginated` já faz internamente.

### Múltiplos CNPJs em `filters[sender_cnpj]`/`filters[receiver_cnpj]`

Já funcionava sem mudança de código, em `listInvoices`, `listTransferInvoices` e `getTransferInvoicesReport` — `sender_cnpj`/`receiver_cnpj` são `filterableFields` comuns (não `customFields`), e o `QueryParser` (`query.parser.ts`) atribui o valor bruto do filtro direto em `where[field]` sem envolver em operador; um array vindo de `filters[sender_cnpj][]=A&filters[sender_cnpj][]=B` vira `where.sender_cnpj = ["A", "B"]`, que o Sequelize já interpreta como `IN (...)` por padrão (comportamento nativo pra array como valor de campo, não precisa de `Op.in` explícito). `stringFields` (`InvoiceService.queryConfig`) já inclui os dois campos, então não sofrem a coerção pra `Number` que a query aplicaria a outros filtros não-string.

### `delivery_note_generated` — filtro boolean + campo calculado, nos dois lados da transferência

Não é uma coluna de `invoices` — é derivado por `helpers/delivery-note.ts` (`deliveryNoteGeneratedLiteral`/`deliveryNoteGeneratedWhere`), reaproveitando a mesma `EXISTS` SQL pros dois usos: `EXISTS (expedition_batch_invoices ebi JOIN expedition_batches eb JOIN unit_businesses ub ON ub.id = eb.unit_business_id WHERE ebi.invoice_id = Invoice.id AND eb.delivery_note_generated_at IS NOT NULL AND ub.cnpj IN (Invoice.sender_cnpj, Invoice.receiver_cnpj))` — verdadeiro se **qualquer uma das duas pontas** (o lote da unit business remetente OU o da destinatária) já teve romaneio gerado, não só a loja logada.

- **Campo calculado** (`deliveryNoteGeneratedLiteral`, em `buildListedInvoiceQueryOptions`'s `attributes.include`): aparece em toda resposta de `listInvoices`/`listTransferInvoices`/`getTransferInvoicesReport` como `delivery_note_generated: boolean`. Pensado pra tela de listagem de nota de transferência mostrar "romaneio gerado" no lugar de `printed_label` — não substitui/remove `printed_label` do payload, é campo adicional.
- **Filtro** (`deliveryNoteGeneratedWhere`, wired como `customFields.delivery_note_generated` em `InvoiceService.queryConfig`): `?filters[delivery_note_generated]=true|false`. `true` vira a mesma `EXISTS`, `false` vira `NOT EXISTS` (nenhuma das duas pontas gerou romaneio ainda). Por ser `customFields` (não `filterableFields`), funciona em `listInvoices`/`listTransferInvoices`/`getTransferInvoicesReport` sem exigir nenhum `include` extra — a `EXISTS` já referencia `Invoice.id`/`sender_cnpj`/`receiver_cnpj` direto, sem depender do join de `unitBusinessAttributes`.

## Provisional/"stub" invoices (`InvoiceService.createStub`) and the 3 shapes of `danfe_path`

Two callers need to link an `invoice_id` FAST (HTTP request path), before the real note is fully known — the slow real import (this file's "`danfe_path` — now actually populated" section above, or the PDV Tecinco XML pipeline) always runs later, in background, and updates the SAME row (matched by `xml_key`/`id_system` via `getFullInvoiceForAllUnits`, see above):
- `bling-order.service.ts::resolveInvoiceId` — order payload already carries `notaFiscal.id` before the `invoice`/`consumer_invoice` webhook finishes. Checks by `id_system` first (cheap, no API call); if nothing found, fetches `GET /nfe/:id` (one call) and, before creating a stub, also checks for an existing row by that response's `chaveAcesso` — the Tecinco/XML import flow (`invoice-xml.ts::upsertInvoiceFromXml`) matches by `xml_key` only and may have already created the real row for this same note (e.g. a note tracked by both integrations). If found, links to that row (backfilling `id_system` if it was still empty) instead of creating a duplicate stub. Only creates a new stub — with both `idSystem` and `xmlKey: nf.chaveAcesso` set — when neither lookup finds a row. Previously `createStub` here was only ever given `idSystem` (never `xmlKey`, even though the already-fetched `nf.chaveAcesso` was available), so a stub could end up permanently un-matchable by `xml_key`; if the Tecinco/XML flow then created its own row for the same note first, both rows survived and any later attempt to enrich either one with the field it lacked hit `invoices_xml_key`/`invoices_id_system`.
- `pdv-sales-request.service.ts::attachTransferInvoice` (`danfeBuffer` branch) — see `.claude/entities/pdv-sales-request/index.md`.

`InvoiceService.createStub({ id?, integrationsId, numberSystem, idSystem?, xmlKey?, danfePath?, senderCnpj?, senderName? })` fills only what the caller already has; every other NOT NULL column (`customer_name`, `customer_document`, `sender_cnpj`/`sender_name` when not given, `receiver_cnpj`, `receiver_name`) gets `""`, never a caller-invented placeholder word. `store_id` always resolves to the `Store` named `"Outros"` via `storeService.findOne` (never `findOrCreate` — throws a clear error if that row is missing, instead of writing an invalid `store_id`). Because it's a plain `this.create(...)` (inherited `BaseService.create`, not `createWithRelations`), a stub row gets **no** `InvoiceUnitBusinessAttributes` and **no** "Nova nota fiscal recebida" notification at creation time.

**Fixed — stub row stayed WITHOUT `InvoiceUnitBusinessAttributes` forever, even after the real background import fully enriched it.** The real import (`invoice-xml.ts`'s `upsertInvoiceFromXml` for Tecinco, `bling-api-fetch.queue.ts`'s `fetchAndUpsertInvoice` for Bling) matches the stub by `xml_key`/`id_system` and always takes the **UPDATE** branch (`updateInvoicesForAllUnitBusiness`) — `InvoiceUnitBusinessAttributes` rows are only ever created by the **CREATE** branch (`createWithRelations`), so a stub-originated invoice, once "found" instead of "created", never got them at all, no matter how many times it was resynced. This broke anything that reads `unitBusinessAttributes.status` for that invoice (status-driven listings/filters, `invoice.controller.ts`'s `status`/`type` custom fields, batch generation eligibility). **Fixed** with `InvoiceService.ensureUnitBusinessAttributes(invoiceId, { senderCnpj?, receiverCnpj?, initialStatus?, invoiceType?, transaction? })` — same sender/receiver-CNPJ→UnitBusiness resolution as `createWithRelations`'s own inline logic (not extracted into a shared helper, to avoid touching that already-tested code path), but idempotent: checks `findInvoiceAttribute` per resolved side before inserting, so calling it on an invoice that already has attributes (the normal case, always true for non-stub invoices) is a no-op. Dedupes by `unit_business_id` within the call (same as `createWithRelations`'s `seen`): when sender and receiver CNPJ resolve to the same UnitBusiness (same-CNPJ note), only one row is created (sender side wins) — otherwise the bulk insert hit `uq_invoice_unit_business_attributes_invoice_unit_business` and the Bling `invoice updated` job failed. Called from both `invoice-xml.ts` and `bling-api-fetch.queue.ts`'s UPDATE branches, right after `updateInvoicesForAllUnitBusiness`, unconditionally (cheap enough, and self-heals if this ever regresses again) — not only when the invoice is known to be stub-originated.

`danfe_path` now has 3 possible shapes, all handled by `getDanfeBuffer`:
1. **Internal, finalized** (the pre-existing case documented above) — `uploaderService.getFile(path)`.
2. **`temp://<tempFileId>` sentinel** — set by `attachTransferInvoice` when staging the DANFE the PDV user just uploaded (`tempFileService.create` + `uploaderQueue.enqueueUpload(..., "INVOICE_DANFE")`, same instant-response pattern as `PDV_SALES_REQUEST_RECEIPT`). `getDanfeBuffer` reads the raw buffer straight from `temp_files` while it's still in staging, with a race fallback (upload finished between the check and now) that reloads and serves via `uploaderService`. `FINALIZE_CHECKERS.INVOICE_DANFE` (`uploader-finalizers.ts`) had to learn to treat this sentinel as "still pending" — it used to be a bare truthiness check (`danfe_path` accepts `NULL`, so any non-null value meant "already uploaded"), which would have made the reconcile sweep delete the still-in-flight `temp_files` row out from under the async upload the moment a stub set a non-null placeholder.
3. **Raw external URL** (`http...`) — set directly by `bling-order.service.ts::resolveInvoiceId` from Bling's own `linkPDF`, no download involved (that's the whole point of the fast path). `getDanfeBuffer` fetches it directly via `fetch()`, **never through `uploaderService`** — `uploaderService`'s axios client (`uploaderApi`) attaches a hardcoded Basic-Auth header for the internal storage backend to every request it makes, absolute URL or not, so routing an external URL through it would leak that credential to the third-party host. This guard didn't exist before because `danfe_path` never held an external URL prior to this stub feature.

## Labels pagination — `GET /invoice/labels/data`

Volumes are never rows in a table — `LabelService` derives them at request time by parsing each invoice's XML (`invoice.xml_path` already holds the raw XML text, not a path/URL) and summing item quantities (`qCom`/`qTrib`) into a `volumeTotal`. Because of that, there is no `volumeTotal` column to page against, and pagination happens entirely in the service layer, not via a Sequelize `LIMIT`.

- **Request**: `invoiceIds` (comma-separated, unchanged), `limit` (page size in volumes, default 50, clamped 1–200), `cursor` (opaque, base64-encoded `{i: invoiceIndex, v: volumeOffset}` — a *positional* pointer into the `invoiceIds` array + an offset of volumes already delivered within that invoice, not a DB cursor).
- **Response**: `{ data: LabelDataDTO[], nextCursor?: string, totalVolumes?: number }`. `data` is grouped by note (one entry per invoice touched in this page, note-level fields sent once, `volumes: LabelVolumeDTO[]` holding only this page's slice) — fixes a pre-existing bug where every volume duplicated all note-level fields via `{...params}` spread in `buildVolumes`. `nextCursor` is omitted on the last page. `totalVolumes` (sum across the whole `invoiceIds` batch) is only computed on the first call (`cursor` absent), via a lightweight XML parse (`countVolumesForInvoices`/`countVolumesFromXml` — just sums quantities, skips `findItemMetaFromInvoiceItems`/`findCarrierRange`/transporter lookup) — deliberately paid twice for invoices that land on later pages (once light for the count, once full when the walker reaches them), a tradeoff accepted over adding a cache since labels are normally printed once.
- **No caching between pages** (deliberate — the batch is a one-shot print, not worth the TTL/staleness complexity of a server-side session). Each invoice's XML is reparsed from scratch whenever the pagination walker reaches it, even mid-invoice across two pages (e.g. a 100-volume note with `limit=50` is parsed twice, once per page).
- **`printed_label`/`label_error` per invoice**: set when the walker finishes delivering *that invoice's* last volume (which can be on any page, not necessarily the first) — `printed_label: true` on success. On a parse failure, `label_error: true` always, and `printed_label: false` **only if it wasn't already `true`** (a failed retry never downgrades a note that was already fully printed in an earlier successful run).
- **`LabelVolumeDTO`/`LabelDataDTO`** (public, trimmed) coexist with the original **`LabelVolume`/`LabelData`** (internal, unchanged) — the internal shape is still used by `LabelService.getInvoiceVolumes(invoiceId, unitBusinessId)` (no side effects, single invoice), whose only external caller is `ExpeditionScanLogService.getPendingVolumesByBatchItem` (`src/modules/warehouse/expedition/scan-logs/scan-logs.service.ts`), which reads `productId`/`volNumber`/`volumeAtual`/`volumeTotal` — fields deliberately dropped from the public DTO but still present on the internal type.
- The old `getLabelData(invoiceIds, unitBusinessId)` (built the whole batch in one shot, no pagination) was removed — confirmed no callers outside `invoice.controller.ts` before deleting it. `/invoice/labels/data` and `getLabelData`/`getLabelDataPage` have no consumer besides the labels screen.

## Cancellation hook into PDV Management
When `upsertInvoiceFromXml` detects `cancelledInvoice` (its own existing `isCancelledInvoice` check, unchanged) or `bling-api-fetch.queue.ts` sees `nf.situacao === 2` on an update, both now call `pdvSalesRequestService.handleInvoiceCancelled(invoice.id)` after the invoice upsert finishes — see `.claude/entities/pdv-sales-request/index.md`. This is the only place invoice cancellation is currently surfaced to another module; it does not change any invoice-side behavior (still sets `invoice_unit_business_attributes.status = PENDING_CANCELLED_SYSTEM`, same as before).
