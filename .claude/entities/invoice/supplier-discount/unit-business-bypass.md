# `getInvoiceProductReport`-only unit-business bypass

Explicit user request — read-only, isolated from the real discount engine on purpose. The real `supplier_discount_value`/`_rule_name` (`report-value.md`) correctly shows `0`/`null` for a note whose STORE isn't in the rule's `unit_business_ids` scope, even if brand/rim/quantity otherwise match — loja is never a wildcard axis, that's the engine working as designed. The user wants this ONE report to show the discount the note WOULD have gotten if store weren't a restriction — e.g. a rule scoped to "Loja 1" only, a note at "Loja 2" with matching brand/aro and enough quantity, still shows the discount here. Explicitly **only this report** ("SÓ NESSE RELATÓRIO! DADO APENAS DE LEITURA") — `getInvoiceSupplierReport` and the `supplier_discount` filter are untouched, still show the real value.

- **New, fully separate code path** — never touches/reuses `matchBatch`/`resolveForItems` (deliberately duplicated, not refactored-to-share, for zero risk to real discount computation): `SupplierDiscountRuleRepository.matchRealRulesIgnoringUnitBusiness` (same brand/rim/measure wildcard-if-empty `EXISTS` shape as `matchBatch`, but **no** `supplier_discount_unit_businesses` join, hardcoded `discount_type = 'REAL'`) → `SupplierDiscountRuleService.resolveRealDiscountsIgnoringUnitBusiness` (same block-decomposition math as `resolveForItems`'s REAL branch, pooled by `pool_id` = **the invoice itself**, not the order — resolves rule names via `findManyDetailedByIds`).
- **PERCENTUAL rules excluded entirely** (explicit user tradeoff) — a percentage needs the item's fiscal value, which this report doesn't fetch (`InvoiceFiscalItem.total_value` would be the source, not wired up). A PERCENTUAL-only rule never appears via this path; REAL-type rules still do.
- **Reference date for the rule's window**: `Order.date` when linked, else `Invoice.emitted_at` — explicit user choice so a note outside the sales pipeline still gets a sensible date to check.
- **Bypass is only a fallback** in the per-item loop: `effectiveDiscount = discount && discount.value > 0 ? discount : bypassDiscount` — a real non-zero discount always wins; bypass fires only when the real lookup found nothing or `0` (missing snapshot, insufficient quantity, or genuinely out-of-scope). Verified against prod: a real invoice at a store never in the rule's `unit_business_ids` showed `0` from the real path and the correct non-zero value once the bypass was added; insufficient quantity, wrong aro, out-of-window date all still correctly yield `0` — only the unit_business axis is bypassed.

## Follow-up bug: `supplier_discount` filter excluded bypass-only rows

The shared `customFields.supplier_discount` (`filter.md`) still only matched the strict `sales_order_item_snapshots` value, so a note qualifying only via the bypass (out-of-scope store) was excluded from the query's `where` before the bypass calculation ever ran. Confirmed with the user's real request (`sender_cnpj=02316749002111` = "Loja 21 - CD MG", 4 rules scoped to "Loja Pax Meli, Shopee" only) — kept returning the same 127 rows the strict match found, missing the additional out-of-scope-but-otherwise-matching ones.

**Fixed, `getInvoiceProductReport`-only**: `supplier_discount` is stripped from `params.filters` before it reaches the DB `where` (query fetches every candidate row regardless of recorded discount), applied instead as a **post-fetch** filter — after computing `effectiveDiscount` per item, a row is kept only if `effectiveDiscount.ruleId` is one of the selected ids. Required both `buildSupplierDiscountLookup` and `resolveRealDiscountsIgnoringUnitBusiness`'s returned maps to also carry `ruleId` (previously only `value`/`ruleName` — filtering by rule *name* would be wrong, ids can collide in prose). `getInvoiceSupplierReport`/`listInvoices` keep the original DB-level strict filter untouched. Verified: 127→133 rows once the 6 bypass-only-eligible lines were included; filtering by a single rule id among the 4 correctly narrowed back to just that rule's matches. Note: this report has no real pagination to begin with (`BaseRepository.findAll` doesn't apply `limit`/`offset` when called with `params`, pre-existing gap unrelated to this change) — the post-fetch filter doesn't make that better or worse.
