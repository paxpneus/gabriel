# Per-line supplier discount value in reports

`getInvoiceProductReport`/`getInvoiceSupplierReport` rows carry `supplier_discount_value`/`supplier_discount_rule_name`. Not computed here — read from `SalesOrderItemSnapshot.supplier_discount_value`/`.supplier_discount_rule_id` (written once, hourly, by `SalesReportQueue.applySupplierDiscounts`, see `../../../modules/reports.md`), keyed by `(order_id, product_id)`, **not** `invoice_item_id` (the snapshot is an order-side concept; the same sale is visible from both `Order`/`InvoiceItems`, joined only via `Invoice.order` + matching `product_id`).

Same `.init()` gap `Product.category` had (see `../../product/index.md`): `m240` added the columns to the DB but they were missing from `sales-order-item-snapshot.model.ts` — fixed by adding both to the model's class/`.init()`/`Attributes` type.

Pipeline: `InvoiceRepository.findSupplierDiscountsByOrderIds(orderIds)` (queries `SalesOrderItemSnapshot` directly — no repository/service of its own, same accepted exception as `InvoiceFiscalItem`) → `InvoiceService.buildSupplierDiscountLookup` (private, shared by both report methods) builds a `Map<"orderId|productId", {value, ruleName, ruleId}>`, resolving `supplier_discount_rule_id → name` via `supplierDiscountRuleService.findManyDetailedByIds`. A line with no matching snapshot row (no order, or never priced through `SalesReportQueue`) reports `0`/`null`, not an error.

## Two real bugs found testing directly against production data

Confirmed via `psql` + a standalone `tsx` script calling the service functions directly — neither caught by `tsc`, both runtime-only:

1. **KIT/component mismatch.** A tire sold as a KIT has ONE `sales_order_item_snapshots` row keyed by the **KIT's own** `product_id` (`order_items.product_id` is the kit) — but the NF-e never has a "kit" line item, only the physical **component**(s) (`invoice_items.product_id` is the tire). Since tire discount rules are typically "a cada 2 pneus" (sold as kit-of-2), this hit essentially every real row: the naive `(order_id, product_id)` key never matched. **Fixed** by `InvoiceRepository.findKitComponentsByKitIds(kitProductIds)` (queries `KitComponent` directly, same no-service exception) + `buildSupplierDiscountLookup` now also registers each kit's discount under `(order_id, component_product_id)` for every component, alongside the kit's own id — a non-KIT sale (no `kit_components` row) only gets the direct entry, unchanged.
2. **Missing `Product.id` in the report's own `attributes` list.** Both report queries' `Product` include already had explicit `attributes: [...]` (`["line"]` / `["name", "brand"]`) — Sequelize does **not** auto-add an included association's PK just because it's needed to build the nested object; an include with explicit `attributes` returns exactly what's listed, no implicit PK. `item.product.id` came back `undefined` for every row, so the lookup key was always `"<orderId>|undefined"` — silently matching nothing, no error thrown. **Fixed** by adding `"id"` to both attribute lists. If a new report/method adds a model include with a hand-picked `attributes` array and later needs `.id` off it: it's not implicit, list it.
