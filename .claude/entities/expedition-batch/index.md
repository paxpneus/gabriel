# Expedition batch entity

`src/modules/warehouse/expedition/`

Split by subject:

- `add-invoice-to-batch.md` — bulk `addInvoiceToBatch` rewrite + batch-numbering fix

- `batch/batch.repository.ts` — `getFullBatch`/`getFullBatches` build a nested include (invoice, batchInvoices, items → product → productConfigs/stocks), all scoped by the batch's own `unit_business_id` via `buildFullIncludes(unitBusinessId)`. A `ProductConfig` include cross-store leak here was found and fixed — any future change to this include must keep `where: { unit_business_id }` on both the `ProductConfig` and `Stock` sub-includes.
- `scan-logs/scan-logs.service.ts` — matches a scanned physical label against `ProductConfig.gtin` (stripped of leading zeros too) OR the already-resolved `matchedCode` (SKU/mapping code). `gtin_package` matching removed in `m265` (see `../product/index.md`).
- `scan-logs.service.ts`'s `getPendingVolumesByBatchItem(batchItemId)` (route `GET /pending-volumes/:batchItemId`) returns, per invoice, the exact `vol_number`s still missing for one `ExpeditionBatchItems` (product in the batch): one row `{ productName, invoiceNumberSystem, vol }` per missing volume.
  - **`vol_number` is NOT a simple per-product sequential number.** Per `invoice-label.service.ts`'s `buildBarcode`/`buildVolNumber`, the physical label barcode is `cnpj(14) + nf(8) + ean(13) + volumeAtual(3) + volumeTotal(3)` (41 chars total — matches `labelcode.length < 41` and the `substring(35, 41)` used when scanning), and `vol_number` stored on `ExpeditionScanLog` is just that last 6-digit `volumeAtual+volumeTotal` suffix. Both `volumeAtual` (1-indexed) and `volumeTotal` count volumes **across the whole invoice** (sum of quantities of every `<det>` line in the NFe XML, in XML order), not per product line — so a product's actual set of volume numbers is whatever slice of that global 1..volumeTotal range its own XML `<det>` line(s) landed on, not `1..quantity_expected`.
  - Because of this, `getPendingVolumesByBatchItem` can't compute expected volumes on its own: it calls `labelService.getInvoiceVolumes(invoiceId, unitBusinessId)` (new public, side-effect-free method on `LabelService` — reuses the same XML parsing as label printing, but skips the `printed_label`/`label_error` flag updates that `getLabelData` does) to rebuild the full list of `LabelVolume`s for that invoice, then filters to the ones whose `productId` matches the batch item's `product_id`, and subtracts whatever `vol_number`s are already in `ExpeditionScanLog` for that `(batchItemId, expedition_batch_invoice_id)` pair.
  - `productId` on `LabelVolume`/`LabelProductVolume` is resolved per XML `<det>` line by `parseNFeXml`, in this priority order: (1) **SKU** — `<det>`'s `cProd` (our own code, since labels are for outgoing invoices) matched against `ProductConfig.sku` for the invoice's unit business (`bySku` map from `findItemMetaFromInvoiceItems`); (2) **GTIN** — `cEAN`/`cEANTrib` matched against `ProductConfig.gtin` (`byGtin` map, same source); (3) **SupplierMapping** — for whatever `<det>` lines still have no match, `supplierMappingService.findByProductCode(code, unitBusinessId)` is called (once per distinct unresolved SKU/EAN, batched via `Promise.all` to avoid N+1) since the NF-e's own EAN doesn't always match the product's registered GTIN (reseller/supplier packaging code); (4) **positional index** — `InvoiceItems` rows ordered by `createdAt ASC` matched to the XML `<det>` array by index, used only as the last resort when none of the above found anything.
    - Index-only correlation used to be the *only* signal (pre-SKU/GTIN/SupplierMapping fix) and was a real bug: `InvoiceItems` row creation order does not always match XML `<det>` order (seen on invoice 5225 — a 2-product NFe where the second XML `<det>` line's `InvoiceItems` row was created first), so it silently swapped `productId` between products sharing an invoice while `produtos`/`ean` (read straight from the XML) stayed correct — `getPendingVolumesByBatchItem` would then report the wrong product's still-pending volumes for a given `batchItemId`.
  - The join query for pending `BatchInvoiceItems` rows (`batchItem`→`product`, `batchInvoice`→`invoice`) lives in `batch-invoice-items.repository.ts`'s `findPendingByBatchItemId`, called via `batchInvoiceItemsService`; the pending predicate (`quantity_read < quantity_expected`) is the shared helper `batch-invoice-items/helpers/pending-filter.ts`'s `pendingQuantityWhere()`, also reused by `syncFromScanning`.
- `batch.controller.ts` (expedition) is in the HIGH unscoped-CRUD list — see `../../modules/auth.md`. Not fixed.
- **Blocked: adding an invoice with unmapped products to a batch**. Both `ExpeditionBatchService.generateBatchFromInvoices` and `.addInvoiceToBatch` call `unmappedInvoiceProductService.findUnmappedByInvoiceIds(invoiceIds, t)` (query lives in `UnmappedInvoiceProductRepository`, per the repository-owns-queries rule in root CLAUDE.md) and throw `"Nota(s) com produtos não mapeados: <numbers>"` before doing anything else if any targeted invoice still has `UnmappedInvoiceProduct` rows with `status: "UNMAPPED"`. In `generateBatchFromInvoices` this is scoped to `notBatched` (invoices actually about to be processed this call, not ones already batched) and sits right before the existing `assertTransshipment` loop.
- **`generateDeliveryNote(batchId, userId)`** is the actual "romaneio gerado" event (sets `delivery_note_generated_at` on `ExpeditionBatch`) — distinct from `generateBatchFromInvoices`, which only adds the invoice to a batch (`invoice.batch_generated = true`) without printing anything. After setting `delivery_note_generated_at`, it calls `pdvSalesRequestService.finishIfDeliveryNoteGenerated(invoiceIds)` (direct cross-module import, same pattern `invoice-xml.ts` already uses for its own PDV hook) — auto-finishes any `PdvSalesRequest` in `SHIPPING` whose sale (and, for `ADT`, transfer) invoice now has a romaneio. See `.claude/entities/pdv-sales-request/index.md` ("Finalização e correção pós-finalização") for the PDV-side logic.
