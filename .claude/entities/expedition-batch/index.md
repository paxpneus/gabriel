- **Formato do `number`** (ENTRANCE/EXPEDITION): `<transportadora>_LOJA<n>_<seq 4 dígitos>` — builder `buildExpeditionBatchNumber` e parser `extractExpeditionBatchSequence` juntos em `src/shared/utils/normalizers/expedition-batch-number.ts` (puro, sem model); `setBatchNumber` (`batch-nomenclature.ts`) usa o builder. Mudou o formato → muda os dois ali (e `EXPEDITION_BATCH_SEQUENCE_SQL_PATTERN`, mesmo formato em regex do Postgres).
- **Sequência de `setBatchNumber`** (todos os tipos, inclusive INVENTORY/DIVERGENCY): `MAX(sequência extraída do number)` do mesmo tipo + unit business, `+ 1` — nunca `count()`. Bug corrigido: com `count() + 1`, excluir lote (hard delete, model sem `paranoid`) baixava a contagem e a checagem de existência, que compara o `number` completo (com transportadora), deixava repetir a sequência com outra transportadora (ex.: `..._CD 17_LOJA21_0860` e `..._CD 12_LOJA21_0860`). O advisory lock (`<tipo>:<unit_business_id>`) só serializa a concorrência. Lotes com formato legado (`EXP_LOJA21_0001_<data>`, `ENT_...`) não casam com a regex e ficam fora do MAX (todos antigos, de sequência baixa). A checagem do `number` completo continua, por causa do `unique` global da coluna.
- `batch/batch.repository.ts` — `getFullBatch`/`getFullBatches` build a nested include (invoice, batchInvoices, items → product → productConfigs/stocks), all scoped by the batch's own `unit_business_id` via `buildFullIncludes(unitBusinessId)`. A `ProductConfig` include cross-store leak here was found and fixed — any future change to this include must keep `where: { unit_business_id }` on both the `ProductConfig` and `Stock` sub-includes.
- `scan-logs/scan-logs.service.ts` — `scanProduct` matches a scanned physical label against `ProductConfig.gtin` (stripped of leading zeros too) OR the already-resolved `matchedCode` (SKU/mapping code). Fallback when neither is on the label: the label's own EAN segment (`substring(22, 35)`, the NF-e `cEAN` zero-padded to 13) is resolved via `productsService.findByCode` (exact 13-char value only, **never** stripped of leading zeros — distinct products can differ only by a leading zero; gtin → SupplierMapping) and must resolve to the same product — covers NF-e EAN being a supplier-mapping code of the product, distinct from both its gtin and the scanned code. `gtin_package` matching removed in `m265` (see `../product/index.md`). "Volume X já lido" checks `label_full_code` **only in the current batch** (`expedition_batch_id`): the same box label is scanned at each stage (sender outgoing, CD incoming/outgoing in transshipment); no DB unique index.
- `scan-logs.service.ts`'s `getPendingVolumesByBatchItem(batchItemId)` (route `GET /pending-volumes/:batchItemId`) returns, per invoice, the exact `vol_number`s still missing for one `ExpeditionBatchItems` (product in the batch): one row `{ productName, invoiceNumberSystem, vol }` per missing volume.
  - **`vol_number` is NOT a simple per-product sequential number.** Per `invoice/labels/services/labels.service.ts`'s `buildBarcode`/`buildVolNumber`, the physical label barcode is `cnpj(14) + nf(8) + ean(13) + volumeAtual(3) + volumeTotal(3)` (41 chars total — matches `labelcode.length < 41` and the `substring(35, 41)` used when scanning), and `vol_number` stored on `ExpeditionScanLog` is just that last 6-digit `volumeAtual+volumeTotal` suffix. Both `volumeAtual` (1-indexed) and `volumeTotal` count volumes **across the whole invoice** (sum of quantities of every `<det>` line in the NFe XML, in XML order), not per product line — so a product's actual set of volume numbers is whatever slice of that global 1..volumeTotal range its own XML `<det>` line(s) landed on, not `1..quantity_expected`.
  - Because of this, `getPendingVolumesByBatchItem` can't compute expected volumes on its own: it calls `labelService.getInvoiceVolumes(invoiceId, unitBusinessId)` (new public, side-effect-free method on `LabelService` — reuses the same XML parsing as label printing, but skips the `printed_label`/`label_error` flag updates that `getLabelData` does) to rebuild the full list of `LabelVolume`s for that invoice, then filters to the ones whose `productId` matches the batch item's `product_id`, and subtracts whatever `vol_number`s are already in `ExpeditionScanLog` for that `(batchItemId, expedition_batch_invoice_id)` pair.
  - `productId` on `LabelVolume`/`LabelProductVolume` is resolved per XML `<det>` line by `parseNFeXml`, in this priority order: (1) **SKU** — `<det>`'s `cProd` (our own code, since labels are for outgoing invoices) matched against `ProductConfig.sku` for the invoice's unit business (`bySku` map from `findItemMetaFromInvoiceItems`); (2) **GTIN** — `cEAN`/`cEANTrib` matched against `ProductConfig.gtin` (`byGtin` map, same source); (3) **SupplierMapping** — for whatever `<det>` lines still have no match, `supplierMappingService.findByProductCode(code, unitBusinessId)` is called (once per distinct unresolved SKU/EAN, batched via `Promise.all` to avoid N+1) since the NF-e's own EAN doesn't always match the product's registered GTIN (reseller/supplier packaging code); (4) **positional index** — `InvoiceItems` rows ordered by `createdAt ASC` matched to the XML `<det>` array by index, used only as the last resort when none of the above found anything.
    - Index-only correlation used to be the *only* signal (pre-SKU/GTIN/SupplierMapping fix) and was a real bug: `InvoiceItems` row creation order does not always match XML `<det>` order (seen on invoice 5225 — a 2-product NFe where the second XML `<det>` line's `InvoiceItems` row was created first), so it silently swapped `productId` between products sharing an invoice while `produtos`/`ean` (read straight from the XML) stayed correct — `getPendingVolumesByBatchItem` would then report the wrong product's still-pending volumes for a given `batchItemId`.
  - The join query for pending `BatchInvoiceItems` rows (`batchItem`→`product`, `batchInvoice`→`invoice`) lives in `batch-invoice-items.repository.ts`'s `findPendingByBatchItemId`, called via `batchInvoiceItemsService`; the pending predicate (`quantity_read < quantity_expected`) is the shared helper `batch-invoice-items/helpers/pending-filter.ts`'s `pendingQuantityWhere()`, also reused by `syncFromScanning`.
- **Lote de nota interna** (`expedition_batches.is_internal`): `GET /api/batch` traz só `false` por padrão (`filters[is_internal]=true` → só internos); excluir lote aceita igual ao de NF-e (só vazio); add-invoice, finalizar/romaneio atuais, `DELETE /batch-invoices/remove/:id` (exceto pelo cancelamento da nota) e todos os scans/remoções de bipagem atuais recusam lote interno; lotes pendentes de saída/CD21/PDV não listam. Fluxo próprio em `/api/invoice/internal/batch/...` (`../invoice/internal.md`); `syncFromScanning` é público pra ele.
- `batch.controller.ts` (expedition) is in the HIGH unscoped-CRUD list — see `../../modules/auth.md`. Not fixed.
- **Blocked: adding an invoice with unmapped products to a batch**. Both `ExpeditionBatchService.generateBatchFromInvoices` and `.addInvoiceToBatch` call `unmappedInvoiceProductService.findUnmappedByInvoiceIds(invoiceIds, t)` (query lives in `UnmappedInvoiceProductRepository`, per the repository-owns-queries rule in root CLAUDE.md) and throw `"Nota(s) com produtos não mapeados: <numbers>"` before doing anything else if any targeted invoice still has `UnmappedInvoiceProduct` rows with `status: "UNMAPPED"`. In `generateBatchFromInvoices` this is scoped to `notBatched` (invoices actually about to be processed this call, not ones already batched) and sits right before the existing `assertTransshipment` loop.
- **Blocked: lote de entrada com nota Bling não conciliada na Bling** (item da nota sem `codigo` na Bling). Só na **entrada do CD21** (`isCd21Entrance`: `type === "INCOMING"` e loja com `number` = `CD21_UNIT_BUSINESS_NUMBER`; outras lojas/etapas não validam, e `POST /bling-reconciliation-check` devolve `{ jobId: null }` — loja = `unitBusinessId` do body ou a do usuário logado) e só notas com `integrations_id` = `getBlingIntegration().id`; vale em `generateBatchFromInvoices` (sobre `notBatched`) e `addInvoiceToBatch` (`assertBlingEntranceReconciled`), **antes** da trava de não mapeados — item sem código na Bling também vira não mapeado (`../unmapped-invoice-product/index.md`, "Não conciliado na Bling"), e a causa a mostrar é a conciliação. Fluxo em 2 etapas:
  1. `POST /bling-reconciliation-check` (`{ invoiceIds }` ou `{ invoiceKey }`) → `enqueueBlingReconciliationCheck`: se algum reprocesso de nota (`blingInvoiceResyncJobId`) ainda está na fila → 409 `{ error: "Aguarde a sincronização da(s) nota(s) X entre Bling e Hub...", syncing: true }`, sem avaliar. Senão enfileira **um** job `invoice_items_check` na `BLING_API_FETCH` (`apiFetch.blingIds` = `id_system` das notas Bling; `resyncBlingIds` = as que têm não mapeado "não conciliado"; jobId `bling-invoice-items-check-<uuid>`, único por avaliação; prioridade 1; retido 1h = validade da avaliação) → 202 `{ jobId, message }`; sem nota Bling → 200 `{ jobId: null }` (gera direto). Polling: `GET /bling-reconciliation-check/:jobId` (`toJobStatus`; jobId sem o prefixo → `not_found`).
  2. O job (`fetchInvoiceItemCodes`, `GET /nfe/{id}` em paralelo) **nunca falha por produto não conciliado**: devolve `{ invoices: [{ blingId, items: [{ codigo, descricao }] }] }` no `returnvalue`. Nota de `resyncBlingIds` com todos os itens com código → enfileira o reprocesso da nota (`resource: invoice`, jobId fixo `bling-invoice-resync-<blingId>` — não duplica, prioridade `MANUAL_IMPORT_PRIORITY`).
  3. `generate-from-invoices`/`add-invoice` recebem `blingCheckJobId`: sem jobId, job expirado/inexistente, `failed`, não `completed`, ou job sem alguma das notas → erro pedindo (re)avaliar; item com `codigo` vazio → `"Nota(s) com produtos não conciliados na Bling. Concilie os produtos da nota antes de gerar o lote: nota <nº> (<link>)"` (link: `invoice/shared/helpers/bling-entrance-url.ts`); tudo com código mas reprocesso da nota ainda na fila → `"Aguarde a sincronização da(s) nota(s) X entre Bling e Hub e tente novamente."`.
  - `add-invoice-to-last-outgoing-batch` não repassa `blingCheckJobId`: com `type` ≠ `OUTGOING` ali, a trava bloqueia.
- **Item entering an already-batched invoice**: every path that adds `InvoiceItems` after the batch exists has to re-sync the batch through `invoiceItemsService.syncBatchesByInvoiceIds(invoiceIds)`. It syncs **every** `ExpeditionBatchInvoice` of the invoice (OUTGOING and ENTRANCE), each one via `syncBatchFromInvoice` (skips FINISHED batch/invoice). It is called at the end of `upsertInvoiceFromXml` (`invoice-xml.ts`, Tecinco/XML reprocess), at the end of the Bling invoice upsert (`bling-api-fetch.queue.ts`) and in `resolveFromCreatedProduct` (product mapped/created closing invoice-linked unmapped rows). Production bug fixed: Tecinco called `addMissingInvoiceItems` without a sync, so the product went into the invoice but not into the batch. The manual flow (`POST /add/item`) has its own incremental sync inside `createInvoiceItemForUnmappedProductsInTx`.
- **List filters on `delivery_note_generated_at`** (`GET /api/batch`): `filters[delivery_note_generated]=true|false` (custom, has/hasn't romaneio) and `filters[delivery_note_generated_at][start|end]=AAAA-MM-DD` (custom, whole days in America/Sao_Paulo via `startOfDayTz`/`endOfDayTz` from `shared/utils/normalizers/date.ts`, inside `Op.and` so it doesn't overwrite `delivery_note_generated`; non-`AAAA-MM-DD` throws). Not the generic `QueryParser` `{start,end}` range: it parses the date as UTC midnight and `setHours` in local time, so `end` cuts at 23:59 of the **previous** day in SP (start=end=today returned nothing).
- **Blocked: invoice whose PDV sales request is in `CRITICAL_ERROR`**. `generateBatchFromInvoices` (`notBatched` ids) and `addInvoiceToBatch` (right after the unmapped check), plus `generateDeliveryNote` (`batchInvoices` ids, **before** writing `delivery_note_generated_at`), call `pdvSalesRequestService.assertNoCriticalErrorForSaleInvoices` → `"Pedido da(s) nota(s) <números> tem erros críticos — ajuste no quadro PDV antes de gerar lote/romaneio"` (400 via each controller's catch). PDV batch actions go through these same 3 methods. See `../pdv-sales-request/index.md` ("Erro crítico").
- **`finishBatch` (`PUT /finish/:batchId`) repeats the romaneio checks before any write** (`finishBatchTransaction`): `assertAdtBatchTransferReferences(fullBatch, "finalizar o lote")` **only for `type = OUTGOING`** (an INCOMING batch at CD21 can receive a CD 12 invoice with no REF) and `assertNoCriticalErrorForSaleInvoices`.
- **Correction letter (carta de correção)**: invoice with `correction_letter_path` (see `../invoice/index.md`, "Carta de correção") is skipped by `assertAdtBatchTransferReferences` (no transfer exists — it should have gone by carrier). `generateDeliveryNote(batchId, operatorId, actorUserId, correctionLetterJustification?)`: batch with such an invoice and no justification (param trimmed, nor `expedition_batches.correction_letter_justification` already saved, `m350`) → `"Nota(s) com carta de correção: <nº>. Informe a justificativa da carta de correção para gerar o romaneio."` before writing. Given justification is saved in the same UPDATE (overwrites) and goes into the romaneio audit (`correction_letter_justification`); batch without a letter ignores it. Param: `correctionLetterJustification` query on `/delivery-note/get`, `correction_letter_justification` body on PDV `/pdv-sales-requests/delivery-note` (same value for every batch). Always free text, not validated against presets: `CORRECTION_LETTER_JUSTIFICATIONS` (`batch.types.ts`) only feeds the front, which replaces `{notas}` and sends the text. Presets listed by `GET /batch/correction-letter/justifications` (`[authenticate]` only, so the CD21 PDV screen can use it; two segments because the base `/:id` is registered first).
- **`generateDeliveryNote`** is the actual "romaneio gerado" event (sets `delivery_note_generated_at` on `ExpeditionBatch`). Only for `status = FINISHED` batches — otherwise throws `"O lote X ainda não foi finalizado..."` before any write (normal route and PDV). Own-logistics batch (CD 12/17): `assertAdtBatchTransferReferences(batchInfo, "gerar o romaneio")` (`batch/helpers/transfer-reference.ts`) — CD 12/17 via `extractTransporterCd` + `ADT_TRANSPORTER_CDS` (PDV `transporter-cd.ts`) on the batch transporter name OR any invoice `transporter_name` (same rule as `findPendingOutgoingByTransporter`); then `transferReferenceService.assertTransferReferences(..., { checkAlreadyUsed: false })` (see `../invoice/index.md`): every invoice's reference must contain the number of an existing transfer invoice between stores (real or stub). "Already linked to another sale" is NOT checked here — the write flows block it. Errors (one message): `"Nota(s) de venda sem número da nota de transferência: <nº>."` / `"Nota(s) de transferência entre lojas não encontradas no sistema: <ref> (ref. a nota de venda <nº>)."` + `"Vincule a nota de transferência (ou anexe a carta de correção da nota, se ela devia ter ido por transportadora) antes de <gerar o romaneio|finalizar o lote>."` Signature `(batchId, operatorId, actorUserId)`: `operatorId` = chosen operator (`userId` query on `/delivery-note/get`, `operator_id` body on PDV), `actorUserId` = logged user. In one transaction: reads before (`lock: UPDATE`), writes `delivery_note_generated_at`/`operator_id` in one `UPDATE` with `COALESCE(col, value)` (direct `repository.bulkUpdate`, so only the first write sticks even with concurrent calls), re-reads after, resolves the operator name (`userService.findById` of the after `operator_id` — with COALESCE the before one is the same or empty) and records an `EXPEDITION_BATCH` UPDATE audit (`batch/helpers/audit.ts` `deliveryNoteGeneratedAudit`, `user_id` = actor, `changes` with `delivery_note_generated_at` + `operator_name` — never the operator uuid; summary "Romaneio do lote X gerado[ novamente]. Operador: <nome>") on every call, including regenerations. Read via `GET /api/batch/:id/audit-logs` (`findAuditLogs`, paginated, 404/400 like products — see `../audit-log.md`). Once filled, `operator_id` can't change via `PUT /:id` / `PUT /bulk` either: service `update`/`bulkUpdate` overrides (`assertOperatorNotChanged`) reject a different value or `null` → `"O operador do romaneio do lote X já foi definido e não pode ser alterado."` (same value passes) — distinct from `generateBatchFromInvoices`, which only adds the invoice to a batch (`invoice.batch_generated = true`) without printing anything. After setting `delivery_note_generated_at`, it calls `pdvSalesRequestService.finishIfDeliveryNoteGenerated(invoiceIds)` (direct cross-module import, same pattern `invoice-xml.ts` already uses for its own PDV hook) — auto-finishes any active `PdvSalesRequest` (any status except FINISHED/CANCELLED/INVOICE_CANCELLED/EXCLUDED) whose sale invoice now has a romaneio (transfer invoice is not required). See `.claude/entities/pdv-sales-request/index.md` ("Finalização e correção pós-finalização") for the PDV-side logic.
