# Last outgoing batch pointer — `unit_businesses.last_outgoing_batch_pending`

Shortcut mechanism so an operator adding invoices to an outgoing batch doesn't need to know/track which batch id is "the one currently being built" for their unit business — the backend tracks it.

- **Migration `m280`**: `unit_businesses.last_outgoing_batch_pending` (nullable UUID, FK → `expedition_batches.id`, `ON DELETE SET NULL`) — points at the last batch an invoice was added to for that unit business. New association: `UnitBusiness.belongsTo(ExpeditionBatch, { foreignKey: "last_outgoing_batch_pending", as: "lastOutgoingBatchPending" })`.
- **`UnitBusinessService.getOrUpdateLastOutgoingBatchNumber(unitBusinessId)`** (`GET /unit-business/last-outgoing-batch-number/get-or-update`, scoped to the logged user's own unit business, `authenticate` only) — does **not** blindly trust the pointer. Queries `ExpeditionBatchService` for the real current pending `OUTGOING` batch (`status != "FINISHED"`, most recent `createdAt`) as the actual source of truth, and self-heals the pointer to match: clears it to `null` if no such batch exists, updates it if stale/wrong, leaves it alone if already correct. Returns the batch's `number` (not id) — the display value the frontend shows/autofills. `UnitBusinessService.update` gained an `options?: { transaction?: Transaction }` param to support being called from inside an existing transaction (used by the write path below).
- **`ExpeditionBatchService.addInvoiceToLastOutgoingBatch(chavesAcesso, unitBusinessId, type, transferInvoiceId?)`** (body `transfer_invoice_id` → `invoices.transfer_invoice_id` + `transfer_invoice_reference = "REF: <n>"`, validado em `updateInvoices`) (`POST /api/batch/add-invoice-to-last-outgoing-batch`, `authenticate` only — **no `userPermissions`**, unlike every sibling batch action; worth checking if deliberate if this endpoint is touched again) — one transaction: reads the unit business's current `last_outgoing_batch_pending`, calls the bulk `addInvoiceToBatch` (`add-invoice-to-batch.md`) passing that as the target `batchId` (or `undefined`, which creates a new batch, if there's no pending one yet), then updates the pointer to the resulting batch's id. Read, write, and pointer update never go inconsistent since they share one transaction.
- **`GET /api/batch/outgoing-pending/search` → `ExpeditionBatchService.searchPendingOutgoing(params, unitBusinessId)`** (usado pelo modal "pesquisar lote" do front e pelo scanner) — filtra `type: "OUTGOING"`, `status IN (OPEN, PENDING)` e a unit business (status e type no `forcedWhere` do topo, não dentro do include de `UnitBusiness`). Sem o filtro de tipo, lote de entrada aparecia como destino de nota de saída.
- **`addInvoiceToBatch` com `batchId`** valida o tipo por nota: nota cujo tipo difere do `found.type` do lote lança erro, exceto transbordo (`transshipment.md`, entrada e saída da mesma loja). Assim nota de saída não entra em lote de entrada mesmo com id escolhido à mão.
