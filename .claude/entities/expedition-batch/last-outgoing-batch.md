# Last outgoing batch pointer — `unit_businesses.last_outgoing_batch_pending`

Shortcut mechanism so an operator adding invoices to an outgoing batch doesn't need to know/track which batch id is "the one currently being built" for their unit business — the backend tracks it.

- **Migration `m280`**: `unit_businesses.last_outgoing_batch_pending` (nullable UUID, FK → `expedition_batches.id`, `ON DELETE SET NULL`) — points at the last batch an invoice was added to for that unit business. New association: `UnitBusiness.belongsTo(ExpeditionBatch, { foreignKey: "last_outgoing_batch_pending", as: "lastOutgoingBatchPending" })`.
- **`UnitBusinessService.getOrUpdateLastOutgoingBatchNumber(unitBusinessId)`** (`GET /unit-business/last-outgoing-batch-number/get-or-update`, scoped to the logged user's own unit business, `authenticate` only) — does **not** blindly trust the pointer. Queries `ExpeditionBatchService` for the real current pending `OUTGOING` batch (`status != "FINISHED"`, most recent `createdAt`) as the actual source of truth, and self-heals the pointer to match: clears it to `null` if no such batch exists, updates it if stale/wrong, leaves it alone if already correct. Returns the batch's `number` (not id) — the display value the frontend shows/autofills. `UnitBusinessService.update` gained an `options?: { transaction?: Transaction }` param to support being called from inside an existing transaction (used by the write path below).
- **`ExpeditionBatchService.addInvoiceToLastOutgoingBatch(chavesAcesso, unitBusinessId, type, description?)`** (`POST /expedition-batches/add-invoice-to-last-outgoing-batch`, `authenticate` only — **no `userPermissions`**, unlike every sibling batch action; worth checking if deliberate if this endpoint is touched again) — one transaction: reads the unit business's current `last_outgoing_batch_pending`, calls the bulk `addInvoiceToBatch` (`add-invoice-to-batch.md`) passing that as the target `batchId` (or `undefined`, which creates a new batch, if there's no pending one yet), then updates the pointer to the resulting batch's id. Read, write, and pointer update never go inconsistent since they share one transaction.
- **New `GET /expedition-batches/outgoing-pending/search` → `ExpeditionBatchService.searchPendingOutgoing(params, unitBusinessId)`** — **likely bug, not fixed**: the method's `UnitBusiness` include puts `status: {[Op.in]: ['OPEN', 'PENDING']}` inside that include's own `where` — but `UnitBusiness` has **no `status` column at all** (checked the model/types). `ExpeditionBatch` itself *does* have exactly that enum (`'OPEN' | 'PENDING' | 'FINISHED'`), strongly suggesting the filter was meant to apply to the batch's own `status` (top-level `where`, "pending outgoing" = not yet `FINISHED`), not the included `UnitBusiness`. As written this fails at the DB level (Postgres: unknown column) whenever this endpoint is actually called — if touched again, this is very likely the first thing to fix.
