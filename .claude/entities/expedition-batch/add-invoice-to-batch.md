# `addInvoiceToBatch` — bulk rewrite + batch-numbering fix

- **Signature changed**: `addInvoiceToBatch(chavesAcesso: string[], ...)` — used to take a single `chaveAcesso: string`. Now adds **multiple** invoices to one batch (or creates one new batch containing all of them) in a single call/transaction. Also gained an optional trailing `externalTransaction?: Transaction` param so a caller (e.g. `addInvoiceToLastOutgoingBatch`, see `last-outgoing-batch.md`) can run it inside its own transaction instead of always opening a new one.
- New validations, all bulk-aware: dedupes/trims the given chaves; every chave must resolve to an existing invoice (`Nota(s) não encontrada(s): <keys>` otherwise) with at least one item (`As seguintes notas não possuem itens: <numbers>`); every invoice in the call must share the same transporter as each other (`ensureSameBy`, `shared/utils/validators/same-not-allowed.ts`, new shared validator) — before, only the *target batch's* transporter was checked against the one invoice being added, there was no cross-invoice check since there was only ever one invoice per call.
- Already-batched detection is bulk too: invoices already in the **target** batch are silently skipped (no reprocessing); invoices already in a **different** batch for this unit business throw `Nota(s) <numbers> já pertence(m) a outro lote nesta unidade`, listing every conflicting number, not just the first.
- **Real bug fixed — new-batch creation always numbered via the `"ENTRANCE"` sequence, even for `type: "OUTGOING"` batches.** `setBatchNumber(...)`'s first argument was hardcoded to `"ENTRANCE"` unconditionally in the no-`batchId` (create-new-batch) branch. Now: `const batchType = type == "OUTGOING" ? "EXPEDITION" : "ENTRANCE"`, passed to `setBatchNumber` instead. Before this fix, every outgoing batch created through `addInvoiceToBatch` (as opposed to `generateBatchFromInvoices`, which already had correct type handling) consumed a number from the *incoming*-batch numbering sequence instead of its own.
- `ExpeditionBatchRepository.findByIdFullBatch` now forwards its `options` (e.g. `{ transaction }`) into the underlying `findById`/`findOne` lookup — needed so bulk `addInvoiceToBatch` can read a batch consistently within its own transaction instead of potentially reading pre-transaction state.
- **Controller-level note**: `POST /expedition-batches/add-invoice` now defaults `unitBusinessId` to the logged user's own (`getUserContext(req).unitBusinessId`) when the request body doesn't supply one — a partial mitigation of this controller's general unscoped-tenant status (`../../modules/auth.md`) for this one action; the body can still override it with an explicit `unitBusinessId`, so the controller-level gap itself is unchanged.
