# Create product from unmapped

Lets a user manually turn a catalog-scoped `UnmappedInvoiceProduct` (`invoice_id: null`, `external_id` populated) into a real `Product`, reusing the existing Bling/Tecinco fetch-and-upsert pipeline instead of duplicating its logic (KIT handling, Magento sync, kardex, per-filial stock — all already work generically once a `Product` exists, so the new code only needs to *produce* one and fall through). **Always user-triggered — no automatic trigger anywhere else**; normal catalog-sync still only registers unmapped rows unless this flag is set.

- Endpoint: `POST /unmapped-invoice-products/:id/create-product` — validates `external_id` is set, resolves the integration (Bling/Tecinco) from `unmapped.integrations_id`, enqueues a job on the **same existing** `BlingApiFetchQueue`/`TCarUpsertQueue` (no dedicated queue). For Tecinco, resolves the user's branch via `resolveTecincoBranchId` (`src/shared/utils/tecinco/resolve-branch-id.ts`, shared with `InvoiceService.importInvoiceXml`) and enqueues a **minimal** payload (`fll_codigo`, `epctb_codigo`, `epctb_nome` placeholder) — the worker fetches the full ERP detail, not the HTTP request.
- **Priority — reuses existing queue infra, no new queue/lock**: `BaseQueueService.add(data, jobId, jobOptions)` accepts an optional `jobOptions.priority` forwarded to BullMQ's native per-job `priority` (lower number = picked first *among prioritized jobs*). Create-product jobs use `priority: 1` on the same `BLING_API_FETCH`/`TCAR_UPSERT` queue as normal sync — no new queue class, no change to `BLING_SHARED_QUEUE_LOCK`'s ranks (see `../../modules/ml-order-pipeline/locks.md`), no equivalent lock for Tecinco. Deliberate simplification after an earlier design (separate `BLING_PRODUCT_CREATE`/`TECINCO_PRODUCT_CREATE` queues with their own lock wiring) was rejected as unnecessary infra. Caveat: BullMQ cannot preempt a job already *running* — `priority` only affects which job is picked up *next*.
  - **Real BullMQ gotcha, confirmed in prod (2026-09) for Tecinco**: a job added *without* `priority` goes into BullMQ's plain `"wait"` FIFO list, not the `"prioritized"` sorted set — and `moveToActive` always drains `"wait"` first, only falling back to `"prioritized"` once `"wait"` is completely empty. This means a no-priority job is picked **before any** prioritized job, no matter how low that job's priority number is — the opposite of what the number suggests. `tecinco-migration.runner.ts`'s catalog sync enqueues product/customer jobs with no `priority` at all, so on `TCAR_UPSERT` a `priority: 1` create-product job sat starved behind the entire sync backlog instead of "jumping the queue" as intended. **Fixed for Tecinco**: `TCarUpsertQueue` (`tecinco-api-fetch.queue.ts`) overrides `add()` to default every job's `priority` to `TCAR_NORMAL_PRIORITY` (2, exported alongside `TCAR_CREATE_PRODUCT_PRIORITY` = 1) when the caller doesn't set one — every job on that queue now lands in the same `"prioritized"` sorted set, so `priority: 1` genuinely wins. `BlingApiFetchQueue` (`BLING_API_FETCH`) was **not** fixed the same way — it still has this exact gotcha (`bling-webhook.orchestrator.ts` sets `priority: 1` only for invoice resources, leaving every other webhook job without a `priority`), so a Bling create-product job can still be starved behind a large sync backlog.
- `fetchAndUpsertProduct` (Bling) / `processProduct` (Tecinco) both gained an `opts.create` flag (default `false`). When `resolveProductWithMapping` finds nothing and `opts.create` is true (or, **Bling-only**, the product is a KIT — see below), instead of registering an unmapped row they call `createProductFromBlingData`/`createProductFromTCarData`:
  1. Calls `productService.create(...)` (try/catch; any failure — EAN conflict, DB constraint — rethrown as `UnrecoverableError`, since it's already-resolved deterministic data: retrying the same input fails the same way) and `integrationMappingService.createOrUpdateIntegrationMapping(...)`.
  2. Calls `unmappedInvoiceProductService.resolveFromCreatedProduct({ externalId, integrationsId, productId })` — finds **every** unmapped row (catalog and invoice-linked alike) matching that exact `external_id` + `integrations_id` and closes each one: the catalog row (`invoice_id: null`, the one that triggered this whole flow) just gets deleted; any `invoice_id`-linked row for the same `external_id` gets `invoiceService.addMissingInvoiceItems(invoice_id, [{product_id, quantity_expected: row.quantity}])` first (idempotent — no-ops if that invoice already has the item, e.g. from a manual mapping in the meantime) and is then deleted too. Still does **not** cascade to unmapped rows sharing only the same EAN/SKU on a *different* `external_id`/invoice from a different supplier — resolving those stays the separate manual flow (`POST /add/item` → `createInvoiceItemForUnmappedProducts`, see `../invoice/item-resolution.md`'s cascade entry), since an EAN shared across different suppliers' invoices isn't guaranteed to be the same physical product. In practice today this closes invoice-linked rows only for Tecinco: it's the only flow that populates `external_id` on `invoice_id`-linked unmapped rows (see `../product/tecinco/catalog-preflight.md`) — Bling's own invoice-unmapped rows still don't carry `external_id`, so they never match here yet.
  3. Returns the product; caller falls through into the rest of `fetchAndUpsertProduct`/`processProduct` exactly as if found by mapping (KIT component sync, Magento sync, `ProductConfig`/`Stock` upsert, kardex) — no duplicated logic.
- **KIT auto-create (Bling only, no `opts.create` needed)**: `blingProduct.formato === "E"` always takes the create branch even without the manual endpoint — a KIT's `ProductConfig.sku` is synthesized from its resolved component's sku + quantity (`${componentSku}K${quantidade}`), inherently unique to that combination, so there's no "this code might belong to a different product" ambiguity to confirm manually. Tecinco has no equivalent — it never syncs KIT composition (no KIT concept in Tecinco-owned catalog data; the `formato === "E"` check never matches there).
- **Job status polling**: `GET /unmapped-invoice-products/:id/create-product/job` → `getCreateProductJobStatus` looks up the job by deterministic id (`bling-product-create-${id}` / `tecinco-product-create-${id}`, tried against both queues), maps BullMQ's `job.getState()` to `{ status, error? }`. Two BullMQ gotchas:
  - A job enqueued with an explicit `priority` sits in BullMQ's `"prioritized"` state (not `"waiting"`) until picked up — reported to the caller as `"waiting"` (frontend doesn't need the distinction).
  - Queue jobs default to `removeOnComplete: true` (instant deletion on success — kept as the `BaseQueueService.add` default for high-volume sync queues), so a finished create-product job would vanish before anyone could poll it, wrongly reporting `"not_found"`. `BaseQueueService.add` now accepts a per-call `jobOptions.removeOnComplete` override; create-product passes `{ age: 24 * 3600 }` (keeps it 24h) — every other `.add()` caller keeps the instant-delete default.
  - Permanent failures use `UnrecoverableError` so `getState()` reports `"failed"` immediately — the queue's default `attempts: 5` exponential backoff (~30s/60s/120s/240s/480s, ~15min total) would otherwise leave `getState()` reporting `"delayed"` for that whole window even for an error certain to fail identically on retry.
- **Error-message convention** for anything reaching an end user through this flow (job `failedReason`, thrown `Error`/`UnrecoverableError` messages): lead with one plain-language sentence a non-technical user can act on (what happened, and for data-inconsistency cases, "encaminhe este erro para o time técnico"), name the actual product(s) by `name` (not just id), put technical detail (ids, field names, code file/function) in `[...]` at the end for whoever it gets forwarded to. See `assertEanNotOwnedByAnotherProduct`'s `EanConflictError` and `SupplierMappingConflictError` for the concrete pattern.

## Combined flow: create product + cascade-map to invoice (`createProductAndMapToInvoice`)

`UnmappedInvoiceProductService.createProductAndMapToInvoice(id, params)` — `POST /unmapped-invoice-products/:id/create-product-and-map` — merges two flows that previously had to be done as separate manual steps for an invoice-linked unmapped row with no matching local `Product`: creating the product from the unmapped row (`createProduct`, above) and mapping that same row to its invoice with the full manual-mapping treatment (`InvoiceItemsService.createInvoiceItemForUnmappedProducts` — `InvoiceItem` + `InvoiceFiscalItem` + batch sync + `SupplierMapping` + automatic cascade to sibling unmapped rows in *other* invoices sharing the same supplier code + sender CNPJ, see `../invoice/item-resolution.md`'s "Manual mapping cascade").

- Only valid for a row with `invoice_id` set (a catalog-scoped row, `invoice_id: null`, has no invoice to map to — use plain `createProduct` for those). Also requires `external_id`, same as `createProduct`.
- **Still fully async** — Bling/Tecinco product creation always goes through the same rate-limited/locked queue infra (`BlingApiFetchQueue`/`TCarUpsertQueue`), so there is no synchronous "create then map" path. The endpoint just enqueues the exact same job as `createProduct` (same job id, same `priority`), with one addition: the job payload also carries `cascadeMapUnmappedId` (the triggering row's own id) — `ApiFetchRequest.cascadeMapUnmappedId` for Bling, a top-level `TCarUpsertJobPayload.cascadeMapUnmappedId` for Tecinco. Front-end polling is unchanged: same `GET /unmapped-invoice-products/:id/create-product/job` endpoint, since it looks up the job by the same deterministic id.
- **Worker-side wiring**: `resolveFromCreatedProduct` gained an optional `excludeIds` — when the product resolves (either by an actual create, `createProductFromBlingData`/`createProductFromTCarData`, or by the Bling-only SKU automap fallback, `autoMapExistingProductBySku`; Tecinco's SKU/mapping automap **never** runs under `create:true`, so it doesn't need this), each queue class's `resolveUnmappedAndCascade` private helper calls `resolveFromCreatedProduct` with `excludeIds: [cascadeMapUnmappedId]` (skipping the triggering row from the bare `addMissingInvoiceItems`-only closing that every other matching row still gets), then loads that one row by id and calls `invoiceItemsService.createInvoiceItemForUnmappedProducts` on it directly with the resolved `productId` — reusing the exact same cascade-to-siblings logic the manual `/add/item` flow uses, instead of duplicating it.
- **Deliberately scoped to this route only** — `resolveFromCreatedProduct`'s default behavior (no `excludeIds`, no rich cascade) is unchanged for every other trigger (Bling/Tecinco webhooks, KIT auto-create, plain `createProduct`/`createProducts`) to avoid changing already-in-production automatic-resolution behavior. If a future need arises to always do the rich cascade on every product creation, that's a deliberate, separate decision — not a side effect of this endpoint.
